== MySQL 架构与存储引擎

=== 架构分层

连接层 → 服务层（SQL 解析、优化器、执行器、缓存）→ 存储引擎层（InnoDB/MyISAM）。

=== 执行流程

连接器 → 分析器（词法/语法）→ 优化器（索引选择、执行计划）→ 执行器（调用存储引擎）。

=== InnoDB 与 MyISAM

[cols="1,2,2"]
|===
| 对比项 | InnoDB | MyISAM
| 事务 | 支持 | 不支持
| 锁 | 行锁 + 间隙锁 | 仅表锁
| 外键 | 支持 | 不支持
| 崩溃恢复 | redo/undo 支持 | 不支持
| 索引 | 聚簇索引 | 非聚簇
| 场景 | 默认、在线事务 | 只读/低并发
|===

== 常用 SQL 语句

以下示例以 MySQL 8.0 为主，窗口函数、CTE 需 8.0+；字符集统一用 `utf8mb4`。

=== DDL 数据定义

[source,sql]
----
CREATE DATABASE IF NOT EXISTS demo
  DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_unicode_ci;

CREATE TABLE t_user (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  username    VARCHAR(64)  NOT NULL COMMENT '用户名',
  age         TINYINT      NOT NULL DEFAULT 0,
  status      TINYINT      NOT NULL DEFAULT 1,
  created_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_username (username),
  KEY idx_status_created (status, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

ALTER TABLE t_user ADD COLUMN email VARCHAR(128) NULL AFTER username;
ALTER TABLE t_user MODIFY COLUMN age SMALLINT NOT NULL DEFAULT 0;
ALTER TABLE t_user DROP COLUMN email;
ALTER TABLE t_user ADD INDEX idx_age (age);
RENAME TABLE t_user TO t_user_new;
TRUNCATE TABLE t_user_new;   -- 清空并重置自增，DDL 不可回滚
DROP TABLE IF EXISTS t_user_new;
----

- DDL 会隐式提交事务，不可 `ROLLBACK`；大表变更用 `gh-ost` / `pt-osc` 在线执行。
- `TRUNCATE` 比 `DELETE` 快但不写 binlog 行级日志、不触发触发器、不可回滚。

=== DML 数据操作

[source,sql]
----
INSERT INTO t_user (username, age) VALUES ('alice', 18), ('bob', 20);
INSERT INTO t_user (username, age)
  SELECT username, age FROM t_user_bak WHERE status = 1;

-- 主键/唯一键冲突则更新（UPSERT）
INSERT INTO t_user (id, username, age) VALUES (1, 'alice', 20)
  ON DUPLICATE KEY UPDATE age = VALUES(age), updated_at = NOW();

REPLACE INTO t_user (id, username) VALUES (1, 'alice');  -- 冲突先删再插，慎用

UPDATE t_user SET age = age + 1, status = 2 WHERE id = 1;
DELETE FROM t_user WHERE status = 0 AND created_at < '2025-01-01';
----

- `UPDATE` / `DELETE` 务必带 `WHERE` 且命中索引，否则全表扫描并锁大量行。
- 大批量删改分批执行（如每批 1000 条），避免大事务与主从延迟。

=== 基础查询

[source,sql]
----
SELECT id, username, age FROM t_user
WHERE status = 1 AND age BETWEEN 18 AND 30;

SELECT DISTINCT status FROM t_user;
SELECT * FROM t_user WHERE username LIKE 'a%' ORDER BY created_at DESC LIMIT 10 OFFSET 20;
SELECT * FROM t_user WHERE id IN (1,2,3) AND deleted = 0;
SELECT * FROM t_user WHERE email IS NULL;
SELECT u.id, u.username AS name FROM t_user u WHERE u.age >= 18;
----

- 避免 `SELECT *`（无法走覆盖索引、网络开销大）；`LIKE '%xx'` 前导通配不走索引。
- 判断 `NULL` 用 `IS NULL` / `IS NOT NULL`，`= NULL` 永远为假。
- 注意隐式类型转换（字符串列传数字会导致索引失效）。

=== 聚合与分组

[source,sql]
----
SELECT COUNT(*) AS cnt, COUNT(DISTINCT username) AS uniq,
       SUM(amount) AS total, AVG(amount) AS avg_amt, MAX(amount), MIN(amount)
FROM t_order WHERE status = 'PAID';

SELECT status, COUNT(*) AS cnt
FROM t_order
GROUP BY status
HAVING COUNT(*) > 10
ORDER BY cnt DESC;
----

- `WHERE` 在分组前过滤行，`HAVING` 在分组后过滤组。
- `COUNT(*)` 统计行数，`COUNT(col)` 不计 `NULL`；`GROUP BY` 后 `SELECT` 列必须是分组列或聚合结果。
- 分组/排序字段有索引可避免 `Using temporary` / `Using filesort`。

=== 连接查询

[source,sql]
----
-- 内连接：只保留两表都匹配的行
SELECT u.id, u.username, o.order_no
FROM t_user u INNER JOIN t_order o ON o.user_id = u.id;

-- 左连接：保留左表全部，右表无匹配补 NULL
SELECT u.id, o.order_no FROM t_user u LEFT JOIN t_order o ON o.user_id = u.id;

-- 找「没有订单的用户」
SELECT u.id FROM t_user u LEFT JOIN t_order o ON o.user_id = u.id WHERE o.id IS NULL;

-- 自连接（查上下级）
SELECT e.name, m.name AS manager FROM emp e LEFT JOIN emp m ON e.manager_id = m.id;

-- 结果集合并
SELECT id FROM a UNION     SELECT id FROM b;   -- 去重
SELECT id FROM a UNION ALL SELECT id FROM b;   -- 不去重，性能更好
----

- `JOIN` 字段必须建索引；优化器通常小表驱动大表（`EXPLAIN` 可看驱动顺序）。
- `LEFT JOIN` 中，右表的过滤条件放 `ON` 还是 `WHERE` 结果不同：放 `WHERE` 会把未匹配的行也过滤掉，等价于内连接。
- 能用 `UNION ALL` 就不用 `UNION`，省去去重排序。

=== 子查询与 CTE

[source,sql]
----
SELECT * FROM t_user WHERE id IN (SELECT user_id FROM t_order WHERE amount > 100);
SELECT * FROM t_user u WHERE EXISTS (SELECT 1 FROM t_order o WHERE o.user_id = u.id);

-- CTE：把中间结果命名，复杂查询更清晰
WITH dept_stat AS (
  SELECT dept_id, COUNT(*) AS cnt FROM emp GROUP BY dept_id
)
SELECT d.name, s.cnt FROM dept d JOIN dept_stat s ON s.dept_id = d.id;

-- 递归 CTE：查树形/层级结构
WITH RECURSIVE cte AS (
  SELECT id, parent_id, name, 1 AS lvl FROM category WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.parent_id, c.name, t.lvl + 1
  FROM category c JOIN cte t ON c.parent_id = t.id
)
SELECT * FROM cte;
----

- 子查询结果集大时优先改写为 `JOIN` 或 `EXISTS`；`IN` 里的常量列表不宜过长。
- 派生表（FROM 后的子查询）必须起别名；CTE / 递归 CTE 需 MySQL 8.0+。

=== 常用函数

[source,sql]
----
-- 字符串
SELECT CONCAT(username, '@x.com'), LENGTH(username), SUBSTRING(username,1,3),
       REPLACE(username,'a','A'),
       GROUP_CONCAT(DISTINCT username ORDER BY username SEPARATOR ',')
FROM t_user GROUP BY status;

-- 日期
SELECT NOW(), CURDATE(), DATE_FORMAT(created_at,'%Y-%m-%d') AS d,
       DATEDIFF(NOW(), created_at) AS days, DATE_ADD(NOW(), INTERVAL 7 DAY);

-- 数值与条件
SELECT ROUND(amount,2), CEIL(amount), FLOOR(amount), ABS(-1) FROM t_order;
SELECT IF(status=1,'正常','禁用') AS status_txt,
       IFNULL(email,'-') AS email2,
       COALESCE(email, phone, 'N/A') AS contact,
       CASE WHEN age < 18 THEN '未成年'
            WHEN age < 60 THEN '成年'
            ELSE '老年' END AS age_group
FROM t_user;
----

- 对索引列套函数（如 `DATE_FORMAT(created_at,...)`）会导致索引失效，应改写成范围条件。
- `GROUP_CONCAT` 有长度限制（`group_concat_max_len`），大数据量需调整或业务层拼接。

=== 窗口函数（MySQL 8.0+）

[source,sql]
----
SELECT dept_id, name, salary,
       ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn,
       RANK()       OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rk,
       DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dr
FROM emp;

-- 分组取 TopN：每个部门薪资最高的人
SELECT * FROM (
  SELECT e.*, ROW_NUMBER() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rn FROM emp e
) t WHERE t.rn = 1;

-- 累计值与前后行
SELECT order_date, amount,
       SUM(amount) OVER (ORDER BY order_date) AS running_total,
       LAG(amount,1)  OVER (ORDER BY order_date) AS prev_amount,
       LEAD(amount,1) OVER (ORDER BY order_date) AS next_amount
FROM t_order;
----

- 窗口函数「不合并行」：每行都保留，同时能拿到分组内的排名/累计值；普通 `GROUP BY` 会聚合成一行。
- 排名区别：`ROW_NUMBER` 不并列、`RANK` 并列跳号（1,1,3）、`DENSE_RANK` 并列不跳号（1,1,2）。
- 窗口函数不能出现在 `WHERE` 中，需包一层子查询过滤。

=== 事务控制

[source,sql]
----
START TRANSACTION;    -- 或 BEGIN
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;
COMMIT;               -- 出错则 ROLLBACK;

SAVEPOINT sp1;
ROLLBACK TO SAVEPOINT sp1;

SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT @@transaction_isolation;

SELECT * FROM account WHERE id = 1 FOR UPDATE;         -- 当前读，排他锁
SELECT * FROM account WHERE id = 1 LOCK IN SHARE MODE;  -- 共享锁
----

- `FOR UPDATE` 必须在事务内、且必须走索引，否则加锁范围扩大甚至锁表。
- 注意 `autocommit` 默认值；DDL 会隐式提交，事务中不要夹 DDL。

=== 面试高频写法

[source,sql]
----
-- 行转列：按月统计各状态订单数
SELECT DATE_FORMAT(created_at,'%Y-%m') AS m,
       SUM(CASE WHEN status='PAID'   THEN 1 ELSE 0 END) AS paid_cnt,
       SUM(CASE WHEN status='CANCEL' THEN 1 ELSE 0 END) AS cancel_cnt
FROM t_order GROUP BY m;

-- 去重：每个用户只保留最新一条订单
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM t_order o
) t WHERE t.rn = 1;

-- 深分页优化：延迟关联，先取主键再回表
SELECT o.* FROM t_order o
JOIN (SELECT id FROM t_order WHERE status='PAID' ORDER BY id LIMIT 100000, 10) t
  ON t.id = o.id;
----

=== 书写易错点

- `WHERE` 中不要用 `!=`、`NOT IN` 大面积过滤，容易全表扫描；`NOT IN` 遇 `NULL` 结果为空集。
- 字符串比较注意字符集/排序规则不一致导致索引失效或隐式转换。
- `ORDER BY` + `LIMIT` 无确定排序字段时分页结果可能重复/缺失，追加唯一键（如 `ORDER BY id`）兜底。
- 聚合查询注意 `NULL` 语义：`SUM` 忽略 `NULL`，全为 `NULL` 时返回 `NULL` 而非 0，可用 `IFNULL(SUM(...),0)`。
- 别在事务里做远程调用、大循环等耗时操作，避免长事务。

== 索引

=== 索引模型

- *B+ 树*：非叶子节点只存键值、叶子节点存完整数据并用双向链表连接，适合范围查询与磁盘预读。
- 对比哈希索引：只支持等值，B+ 树支持范围与排序。

=== B+ 树层级与容量估算

面试常问「一张表能存多少数据 / 为什么千万级还是 3 层」，核心就是下面这两个估算值。

==== 前提与两个关键数字

- InnoDB 默认页大小 `innodb_page_size = 16KB`（可配 4/8/16/32/64KB）。页是内存与磁盘之间 I/O 的最小单位，*B+ 树的每个节点就是一个页*。
- *扇出 fan-out*：非叶子节点存「主键值 + 子页指针」。设主键为 `BIGINT`（8B）+ 子页页号（4B）+ 记录头等开销（约 2B）≈ 14B，则 `16KB / 14B ≈ 1170`，即一个非叶子页约放 *1170 个索引项*，指向 1170 个子页。
- *叶子容量*：聚簇索引的叶子存整行，设平均行 1KB，扣除页头、页目录、文件尾等开销后，一页约放 *16 行*。

说明：页头（File Header / Page Header / Infimum / Supremum / File Trailer）占几百字节，页填充率通常约 15/16（预留更新空间），页分裂还会产生碎片，实际数值略低于理论值，但量级估算足够。

==== 每层大概有多少索引数据

以「3 层 B+ 树 + `BIGINT` 主键 + 行 1KB」为例：

[cols="1,2,3,3"]
|===
| 层级 | 页数 | 每页内容 | 该层总量（约）
| 第 1 层：根 | 1 | 1170 个「主键 + 子页指针」 | 1170 个索引项
| 第 2 层：中间 | 1170 | 1170 个「主键 + 子页指针」 | 1170 × 1170 ≈ 137 万个索引项
| 第 3 层：叶子 | 137 万 | 16 行完整数据（聚簇索引） | 137 万 × 16 ≈ 2190 万行
|===

- *非叶子层*（根 + 中间）总共只有 1 + 1170 ≈ 1171 个页 ≈ *18MB*，几乎可以全部常驻 Buffer Pool，所以这部分基本不产生磁盘 I/O。
- *叶子层*才是数据主体：137 万个页 ≈ *22GB*。
- 二级索引的叶子只存「索引列 + 主键」，条目远小于整行，单页可放数百到上千条；但叶子不含完整数据，需要回表。

==== 不同树高可存多少行

设扇出 F ≈ 1170、叶子每页 R ≈ 16 行，则「可存行数 ≈ F 的 (h-1) 次方 × R」：

[cols="1,2,2,2"]
|===
| 树高 h | 叶子页数 | 约可存行数 | 典型数据规模
| 1 | 1 | ~16 | 空表 / 极小表
| 2 | 1170 | ~1.9 万 | 几万行
| 3 | 137 万 | ~2190 万 | 千万级（最常见）
| 4 | 16 亿 | ~256 亿 | 理论值，实际极少达到
|===

结论：InnoDB 的 B+ 树一般只有 *2~4 层*，单表到千万级通常仍是 *3 层*，一次主键等值查询最多 3 次页读取；根页与中间页常驻内存，实际物理磁盘 I/O 往往只有 1 次（读叶子页）甚至 0 次（命中 Buffer Pool）。

==== 影响估算的变量

- *主键长度*：`INT`(4B) 的扇出比 `BIGINT`(8B) 更大；用 `UUID` / 长字符串（32B+）作主键，扇出可能降到 300~500，树高容易 +1，且随机插入引发页分裂与碎片。
- *行长度*：行 100B 时一页可放约 150 行，3 层可存约 2 亿行；行 1KB 时只有约 2000 万行。所以大字段（TEXT/BLOB）应垂直拆分、避免 `SELECT *`。
- *页大小*：改为 32KB/64KB 扇出翻倍，但单次 I/O 成本与 Buffer Pool 效率要权衡。
- *填充率与碎片*：乱序插入（尤其 UUID 主键）、更新变长列使行变长、或更新索引列导致索引项搬家，都可能触发页分裂；分裂后两页各约半满，实际容量低于理论值，必要时 `OPTIMIZE TABLE` 重整（详见「页分裂：为什么更新也会触发」）。

==== 实践意义

- 这解释了 *为什么 B+ 树比 B 树更适合做索引*：B 树非叶子节点也存数据，扇出小、树更高、I/O 次数更多；B+ 树把数据全压到叶子层，换来了极大的扇出和极矮的树。
- 也解释了 *为什么千万级要考虑分库分表*：瓶颈通常不是树高，而是 Buffer Pool 命中率下降、锁竞争、索引维护成本、备份恢复与 DDL 时间变长。
- 想估算真实表：`SHOW TABLE STATUS LIKE 't_user'` 看 `Avg_row_length`、`Data_length`、`Index_length`；想看真实树高和页分布，可用 `innodb_ruby` 等工具分析表空间。

=== 聚簇索引与二级索引

- *聚簇索引*（主键索引）：叶子节点存整行数据，一张表一个。
- *二级索引*：叶子节点存主键值，需回表。
- *覆盖索引*：查询列全在索引中，不回表。
- *回表*：二级索引查主键后再到聚簇索引取数据。

=== 页分裂：为什么更新也会触发

先纠正一个常见误解：「索引里只有索引键或主键」只对 *非叶子节点* 成立。InnoDB 各层实际存的内容是：

[cols="1,3"]
|===
| 节点 | 存储内容
| 聚簇索引·非叶子 | 主键值 + 子页指针（确实只有键和指针）
| 聚簇索引·叶子 | *整行数据*（所有列，含变长字段、大字段前缀）
| 二级索引·非叶子 | 索引列值 + 主键 + 子页指针
| 二级索引·叶子 | 索引列值 + 主键值（用于回表）
|===

InnoDB 的聚簇索引 *就是表本身*，叶子页里放的是完整行记录，而不是一个主键。因此「一页能放多少」取决于 *行的实际字节数* 和 *索引项个数*，不只是键的大小。

==== 更新触发页分裂的两条路径

. *行变长，当前叶子页放不下*：把 `VARCHAR` 从短值改成长值、`NULL` 改成有值、填充 `TEXT` 大字段等，行的字节数增加。InnoDB 先尝试用页内剩余空间（含预留的约 1/16），不够就把约一半记录搬到新页 —— 这就是页分裂。注意：即使主键没变、索引键没变，只要行变长且页已满，就会分裂。
. *更新了索引列，索引项要「搬家」*：B+ 树按索引列有序。执行 `UPDATE t SET age = 30 WHERE age = 20` 时，二级索引 `idx_age` 中的这条记录不能原地改，必须从「20 的位置」移到「30 的位置」，实现上是 `delete-mark + insert`；若目标页已满，该页就分裂。更新主键代价更重：聚簇索引整行迁移，且 *所有二级索引叶子里的主键值* 都要同步改写。

补充：叶子页分裂后要往父节点插入新的「键 + 子页指针」，父页若也满则 *级联向上分裂*，极端情况下波及根页、使树高 +1。

==== 哪些更新不会分裂

- 更新的是非索引列，且行长度不变或变短（如 `INT` 状态值改写）→ 通常原地更新。
- 页内还有足够空闲空间 → 变化被预留空间吸收。
- 因此「频繁更新可能导致页分裂」是 *概率性* 的，取决于是否涉及索引列、行长度是否增长、目标页是否已满，并非「只要 UPDATE 就一定分裂」。

==== 代价与规避

- 代价：移动约半数记录、维护父节点指针、可能级联分裂；分裂后两页各约半满，*填充率下降、空间放大*，碎片让同样层数能存的数据变少，也降低 Buffer Pool 命中率。
- 规避：主键用自增 `BIGINT`（顺序追加，只在尾页分裂）而非 UUID（随机落点，到处分裂）；大字段垂直拆表；避免频繁更新索引列；按主键顺序批量导入；必要时 `OPTIMIZE TABLE` 重整。

=== 最左前缀原则

- 联合索引 `(a, b, c)` 遵循最左前缀：`a`、`a,b`、`a,b,c` 可用，`b,c` 无法走索引。
- 原因：索引按字段顺序排序，跳过前导列无法定位。
- `范围查询` 会中断后续列的使用（如 `a=1 AND b>2 AND c=3`，c 无法用）。

=== 索引失效场景

- 对索引列使用函数 / 运算 / 隐式类型转换。
- `like '%xx'` 前导模糊。
- `!= / NOT IN / NOT EXISTS`（部分场景）。
- `OR` 两侧一侧无索引。
- 联合索引不满足最左前缀。
- 优化器判断全表扫描更快（数据量小 / 区分度低）。

=== 索引设计原则

- 高区分度列优先、最左前缀设计、覆盖索引避免回表、避免过多索引（影响写性能）、长字符串用前缀索引、控制索引列数量。

== 事务

=== ACID

- *原子性 Atomicity*：undo log 回滚。
- *一致性 Consistency*：事务前后满足约束。
- *隔离性 Isolation*：锁 + MVCC。
- *持久性 Durability*：redo log 落盘。

=== 隔离级别与问题

[cols="1,2,3"]
|===
| 隔离级别 | 解决 | 未解决
| 读未提交 | - | 脏读、不可重复读、幻读
| 读已提交 RC | 脏读 | 不可重复读、幻读
| 可重复读 RR（默认） | 脏读、不可重复读 | 幻读（MVCC 大部分解决）
| 串行化 | 全部 | -
|===

- 脏读：读到未提交数据。
- 不可重复读：同事务两次读同一行值不同（其它事务 update）。
- 幻读：同事务两次读行数不同（其它事务 insert/delete）。

=== MVCC（多版本并发控制）

- 实现：`undo log` 版本链 + `ReadView`（快照读）。
- 每条记录隐藏列：`DB_TRX_ID`（最近修改事务）、`DB_ROLL_PTR`（undo 指针）。
- 快照读（普通 `select`）通过 ReadView 判断可见性；当前读（`for update`/`update`/`delete`）读最新版本并加锁。
- 版本链：每次修改生成新 undo 版本，回滚指针串联。

=== redo log / undo log / binlog

- *redo log*：物理日志，InnoDB 层，顺序写，循环写（`ib_logfile`），保证崩溃恢复，配合 WAL。
- *undo log*：逻辑日志，回滚与 MVCC，记录旧值。
- *binlog*：Server 层逻辑日志，主从复制与数据恢复，追加写。

=== 两阶段提交（2PC）

- redo log 与 binlog 一致性：`redo prepare → 写 binlog → redo commit`，崩溃恢复时据此判断提交/回滚。

== 锁

=== 锁类型

- 按粒度：全局锁、表锁（`MDL` 元数据锁）、页锁、行锁。
- 行锁：`Record Lock`（记录锁）、`Gap Lock`（间隙锁）、`Next-Key Lock`（记录+间隙，左开右闭）。
- 意向锁：`IS/IX`，表级，标记表中行锁意向，兼容判断。

=== 加锁规则（RR）

- 唯一索引等值命中：退化为记录锁。
- 唯一索引等值未命中：间隙锁。
- 非唯一索引等值：Next-Key Lock 覆盖命中区间。
- 范围查询：Next-Key Lock 到范围末尾。

=== 乐观锁与悲观锁

- 悲观锁：`select ... for update`，先锁后操作，冲突高适用。
- 乐观锁：版本号/时间戳 `version`，提交时比对，冲突低适用；CAS 思想。

=== 死锁

- 产生：两个事务互相等待对方锁。
- 检测：`innodb_lock_wait_timeout`、死锁检测（等待图）。
- 避免：固定加锁顺序、缩小事务、`for update` 谨慎、监控 `SHOW ENGINE INNODB STATUS`。

== SQL 优化

=== 执行计划 EXPLAIN

- 关键字段：`type`（system > const > eq_ref > ref > range > index > ALL）、`key`（实际索引）、`rows`（预估行数）、`Extra`（Using index 覆盖、Using filesort、Using temporary、Using where）。
- `type` 到 `ALL` 需优化。

=== 优化手段

- 索引优化（最左前缀、覆盖索引、避免失效）。
- 减少回表、避免 `select *`。
- 分页优化：深分页用「延迟关联」或 `where id > lastId`。
- 避免大事务、避免长事务（undo 膨胀、锁持有久）。
- 子查询改写 join；`in` 元素过多拆分。
- 批量插入用 `multiValues`；避免隐式转换。
- 大表 `DDL` 用 `gh-ost/pt-osc` 在线变更。

=== 慢查询排查

- 开启 `slow_query_log`，`long_query_time` 阈值；`mysqldumpslow` 分析；定位后 `EXPLAIN` 看计划，针对性加索引或改 SQL。

== 高可用与分库分表

=== 主从复制

- 异步复制：主库写 binlog → 从库 I/O 线程读入 relay log → SQL 线程回放。
- 半同步复制（`semi-sync`）：至少一个从库确认后提交，降低丢失。
- 延迟原因：从库单线程回放（可 `MTS` 并行）、网络、锁冲突。

=== 高可用方案

- 主从 + 手动切换、MHA、MGR（组复制）、Orchestrator 自动故障转移。

=== 分库分表

- 问题：单表数据量过大（千万级）、单库 QPS/容量瓶颈。
- 垂直分库：按业务拆分（用户库、订单库）。
- 垂直分表：大字段/冷热列拆分。
- 水平分表/分库：按 `sharding key` 哈希/范围分片。

=== 分片策略与中间件

- 取模：扩容困难；范围：易热点；一致性哈希：`hash + 虚拟节点`。
- 中间件：ShardingSphere（`Sharding-JDBC`）、MyCat。
- 问题：分布式主键（雪花算法 `Snowflake`）、跨库 join（避免/冗余/宽表）、跨库事务（柔性事务/最终一致）、分页聚合。

=== 分布式主键

- 雪花算法：`1 位符号 + 41 位时间戳 + 10 位机器 ID + 12 位序列号`。
- 优点：趋势递增、高性能；缺点：依赖时钟（回拨问题）。
- 其它：数据库自增段、Redis 自增、UUID（无序，影响 B+ 树插入）。

== 数据库选型详解

=== 总览对比

[cols="1,2,2,2"]
|===
| 数据库 | 类型 | 擅长领域 | 典型场景
| MySQL | 关系型 OLTP | 在线事务、强一致 | 业务核心库
| PostgreSQL | 关系型 OLTP | 复杂查询、JSON、GIS | 复杂业务、分析
| MongoDB | 文档 NoSQL | 灵活 schema、海量文档 | 内容、画像、日志
| Redis | KV 内存 | 缓存、计数 | 缓存层
| ClickHouse | 列存 OLAP | 海量数据批量分析 | 日志/埋点分析
| StarRocks | MPP OLAP | 高并发即席分析、实时数仓 | BI 报表、实时数仓
| HBase | 宽表 NoSQL | 海量写、点查 | 轨迹、时序、风控
| TiDB | NewSQL | 分布式 OLTP + HTAP | 替代分库分表
|===

=== MySQL

- *定位*：最主流的开源关系型 OLTP。
- *擅长*：在线事务、ACID 强一致、复杂关系模型、生态成熟（主从/分库分表/监控工具链）。
- *注意点*：
  - 单表到千万~亿级后查询变慢，需分库分表。
  - 单机写入吞吐有限，复杂 OLAP 分析能力弱。
  - 深分页、大事务、锁等待需重点注意。

=== PostgreSQL

- *定位*：功能最强大的开源关系型，学术/企业级。
- *擅长*：复杂查询、窗口函数、JSON/JSONB、全文检索、GIS（PostGIS）、丰富数据类型、严格 SQL 标准。
- *注意点*：
  - 生态/运维工具略少于 MySQL，DBA 习惯成本。
  - 高并发写时 MVCC 版本膨胀，需 `vacuum` 维护。
  - 水平扩展需第三方（Citus 等）。

=== MongoDB

- *定位*：文档型 NoSQL，BSON 存储，贴近对象模型。
- *擅长*：灵活 schema 快速迭代、嵌套文档、海量数据水平分片、地理索引。
- *注意点*：
  - 跨文档事务有性能代价，不擅长复杂 join。
  - 需精心设计内嵌 vs 引用建模。
  - 内存依赖高（缓存热数据）。

=== ClickHouse

- *定位*：列式 OLAP 数据库，单机分析性能极强。
- *擅长*：海量数据批量分析、实时写入 + 快速聚合、日志/监控/埋点分析、单表查询极快。
- *注意点*：
  - 不适合高频点更新/删除（异步 merge，更新代价高）。
  - 高频点查（小范围主键查询）性能一般。
  - 大表 join 性能需注意，无事务。
  - 适合「写多读少、批量分析」。

=== StarRocks

- *定位*：MPP 架构实时分析数据库（OLAP），向量化执行引擎。
- *擅长*：高并发即席查询、实时数仓、多表 join、物化视图、联邦查询、实时/离线统一。
- *注意点*：
  - 定位分析型负载，不适合高频小事务/随机点更新。
  - 更新用主键模型 + 微批，非随机点更新。
  - 内存资源消耗较大，需合理分桶分区。

=== HBase

- *定位*：基于 HDFS 的宽表 KV NoSQL（BigTable 开源实现）。
- *擅长*：海量写入、稀疏宽表、按 rowkey 点查/范围扫描、天然水平扩展。
- *注意点*：
  - rowkey 设计决定性能，热点需预分区/加盐。
  - 无 SQL 分析能力，需配合 Spark/Hive/Phoenix。
  - 原生无二级索引，运维重（HDFS/ZK/RegionServer）。

=== TiDB

- *定位*：分布式 NewSQL，兼容 MySQL 协议。
- *擅长*：水平扩展 + 强一致事务、HTAP（OLTP + TiFlash 实时分析）、替代分库分表 MySQL。
- *注意点*：
  - 组件多（PD/TiKV/TiDB），部署运维复杂。
  - 复杂查询/大事务性能需调优，资源消耗大。

=== 选型建议

- 核心在线业务、强一致 → MySQL / PostgreSQL。
- 复杂查询、JSON、GIS → PostgreSQL。
- 灵活 schema、快速迭代、海量文档 → MongoDB。
- 缓存/计数 → Redis。
- 海量实时分析、BI 报表 → ClickHouse / StarRocks（高并发即席选 StarRocks）。
- 海量写、轨迹/时序点查 → HBase。
- 想水平扩展又不想改 SQL → TiDB。

== 高频真题与参考答案

=== InnoDB 与 MyISAM 的区别？

- 事务：InnoDB 支持，MyISAM 不支持。
- 锁：InnoDB 行锁 + 间隙锁，MyISAM 仅表锁。
- 崩溃恢复：InnoDB 有 redo/undo，MyISAM 无。
- 索引：InnoDB 聚簇索引，MyISAM 非聚簇（叶子存数据地址）。
- 外键：InnoDB 支持。默认且主流选 InnoDB。

=== B+ 树为什么适合做索引？与 B 树、哈希索引区别？

- B+ 树非叶子节点只存键，单节点能容纳更多索引项、树更矮，减少磁盘 I/O；叶子节点存完整数据并用双向链表连接，天然支持范围查询与排序。
- 对比 B 树：B 树非叶节点也存数据，高度更高；B+ 树范围查询更优。
- 对比哈希：哈希只支持等值查询，不支持范围与排序。

=== 聚簇索引与二级索引？什么是回表与覆盖索引？

- 聚簇索引（主键）：叶子存整行数据，一张表一个。
- 二级索引：叶子存主键值，需先查主键再回表。
- 回表：二级索引 → 主键索引取完整行的过程。
- 覆盖索引：查询列全部在索引中，无需回表，`Extra=Using index`。

=== 最左前缀原则？哪些情况会导致索引失效？

- 最左前缀：联合索引 `(a,b,c)` 必须从最左列连续使用（`a`、`a,b`、`a,b,c`），跳过前导列无法走索引；范围查询会中断后续列。
- 失效：索引列函数/运算/隐式转换、`like '%xx'`、`!=`/`NOT IN`（部分）、`OR` 一侧无索引、不满足最左前缀、优化器认为全表更快。

=== 事务隔离级别？默认级别下如何解决幻读？

- 四级：读未提交、读已提交（RC）、可重复读（RR，默认）、串行化。
- RR 解决幻读：靠 MVCC 快照读（普通 select 读一致性快照）+ 间隙锁（当前读 `for update` 锁住范围），阻止其它事务插入。

=== MVCC 原理？ReadView 如何判断可见性？

- 实现：`undo log` 版本链 + `ReadView`。
- 记录隐藏列：`DB_TRX_ID`（最近修改事务）、`DB_ROLL_PTR`（undo 指针）。
- ReadView 记录活跃事务列表，按「事务 id < min_trx_id 可见、>= max_trx_id 不可见、介于中间查是否在活跃列表」判断版本可见性；快照读走版本链，当前读加锁读最新。

=== redo log 与 binlog 区别？两阶段提交？

- redo log：InnoDB 层、物理日志、循环写，保证崩溃恢复（WAL）。
- binlog：Server 层、逻辑日志、追加写，用于主从复制与恢复。
- 两阶段提交：`redo prepare → 写 binlog → redo commit`，保证二者一致，崩溃时据此决定提交/回滚。

=== InnoDB 有哪些锁？间隙锁解决什么问题？

- 锁：Record Lock（记录）、Gap Lock（间隙）、Next-Key Lock（记录+间隙）、意向锁（IS/IX）、MDL。
- 间隙锁：锁住索引记录间的间隙，阻止其它事务插入，用于 RR 级别解决幻读。

=== 一条 SQL 执行很慢，如何排查？

- 先 `EXPLAIN` 看执行计划（`type` 是否 ALL、是否走索引、`rows`、`Extra` 的 filesort/temporary）。
- 看是否命中慢查询日志，`mysqldumpslow` 分析。
- 检查锁等待（`SHOW PROCESSLIST`、`innodb_lock_waits`）、大事务、隐式转换、深分页等，再针对性加索引/改 SQL。

=== 深分页如何优化？

- 问题：`limit 100000,10` 会扫描并丢弃前 10 万行。
- 方案：延迟关联（先 `select id limit` 再回表）、`where id > lastId` 游标分页、覆盖索引 + 子查询、限制最大页数。

=== 主从复制原理？延迟如何解决？

- 原理：主库写 binlog → 从库 I/O 线程拉取写 relay log → SQL 线程回放。
- 延迟：单线程回放瓶颈、大事务、锁冲突、网络。
- 解决：并行复制（MTS）、半同步、提升从库规格、拆分大事务、监控告警。

=== 分库分表方案？分布式主键如何生成？

- 方案：垂直分库（按业务）、垂直分表（冷热列拆分）、水平分库/分表（按 sharding key 哈希/范围）。
- 主键：雪花算法（趋势递增）、数据库号段、Redis 自增；避免 UUID（无序影响 B+ 树）。

=== 如何保证缓存与数据库一致性？

- 推荐「先更 DB 再删缓存」+ 延迟双删 + 订阅 binlog（Canal）异步删除。
- 本质最终一致；强一致用分布式锁/版本号；写多读少慎用缓存。

=== 大事务有什么危害？

- 锁持有时间长 → 阻塞其它事务、易死锁。
- undo log 膨胀，MVCC 版本链变长，影响查询性能。
- 主从延迟放大，binlog 大事务回放慢。
- 建议拆分为小事务，控制事务时长。
