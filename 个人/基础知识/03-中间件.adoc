== Redis

=== 数据结构与底层实现

[cols="1,2,2"]
|===
| 类型 | 用途 | 底层编码
| String | 缓存、计数、分布式锁 | int / embstr / raw（SDS 简单动态字符串）
| List | 队列、栈、消息列表 | 3.2+ quicklist（ziplist + linkedlist）
| Hash | 对象缓存 | ziplist / hashtable
| Set | 去重、交集 | intset / hashtable
| ZSet | 排行榜、延时队列 | ziplist / skiplist + dict
|===

=== 持久化

- *RDB*：快照，`bgsave` fork 子进程写二进制文件；恢复快，可能丢最近数据；`save 900 1` 等触发。
- *AOF*：追加写命令日志，`appendfsync always/everysec/no`；`AOF` 重写 `bgrewriteaof` 压缩；数据更完整。
- 混合持久化（4.0+）：`AOF` 开头嵌入 RDB，兼顾恢复速度与完整性。
- 数据丢失权衡：`everysec` 最多丢 1 秒。

=== 主从、哨兵、集群

- *主从复制*：全量（RDB）+ 增量（命令传播，`repl_backlog` 环形缓冲区）；读写分离、备份。
- *哨兵 Sentinel*：监控、自动故障转移、通知；哨兵间 Raft 选举 leader 完成主节点切换；主观下线 → 客观下线。
- *Cluster 集群*：`16384` 个哈希槽，`CRC16(key) % 16384` 分槽；主从分片 + 故障转移；`MOVED/ASK` 重定向；数据分片横向扩容。

=== 缓存三大问题

- *穿透*：查不存在数据直达 DB。解决：缓存空值（短 TTL）、布隆过滤器 `BloomFilter`。
- *击穿*：热点 key 失效瞬间大量请求打 DB。解决：互斥锁重建、逻辑过期 + 后台刷新。
- *雪崩*：大量 key 同时失效或 Redis 宕机。解决：TTL 加随机值、多级缓存、集群高可用、限流降级。

=== 一致性

- 先更 DB 再删缓存（推荐）；延迟双删；订阅 binlog（Canal）异步删除。
- 最终一致性为主，强一致需分布式锁或版本号。
- 写多读少 / 强一致场景慎用缓存。

=== 过期与淘汰

- 过期删除：惰性删除（访问时判断）+ 定期删除（周期性抽样）。
- 内存淘汰策略（`maxmemory-policy`）：`noeviction`、`allkeys-lru/lfu`、`volatile-lru/lfu/ttl/random`、`allkeys-random`。

=== 高并发场景

- *分布式锁*：`SET NX EX` + 唯一 token，解锁用 Lua 保证原子删除（比较 token）；`Redisson` 看门狗自动续期 + 可重入。
- *分布式限流*：滑动窗口、令牌桶（Lua + 有序集合）。
- *延迟队列*：ZSet 按时间戳排序 + 轮询；或 Redis Stream。
- *发布订阅*：`PUBLISH/SUBSCRIBE`，不持久，丢消息风险。

=== 线程模型

- Redis 6 前单线程（网络 I/O + 命令执行），但 `bgsave`、AOF 刷盘等有后台线程。
- 6.0 引入多线程 I/O（读/写 socket 并行），命令执行仍单线程保证原子性。
- 快的原因：纯内存、单线程无锁切换、I/O 多路复用（epoll）、高效数据结构。

== 消息队列

=== 为什么用 MQ / 应用场景

- 异步（下单后异步发短信）、削峰填谷（秒杀）、解耦（系统间低耦合）。
- 代价：系统复杂度、可用性降低、一致性问题、重复/丢失/顺序问题。

=== 核心概念对比

[cols="1,1,1,1"]
|===
| 维度 | Kafka | RocketMQ | RabbitMQ
| 定位 | 日志/大数据流，高吞吐 | 金融级消息，事务 | 通用企业级，灵活路由
| 存储 | 磁盘顺序写，日志 | CommitLog 顺序写 | 队列内存+磁盘
| 吞吐 | 极高 | 高 | 中
| 顺序 | 分区内有序 | 队列内有序（顺序消息） | 单队列有序
| 延迟 | 中 | 低（支持定时/事务） | 低
| 事务 | 不重点 | 事务/半消息 | 较少用
| 协议 | 自有 | 自有（类 Kafka 设计） | AMQP
|===

=== 为什么 Kafka 吞吐远高于 RabbitMQ

先纠正一个说法：准确讲是 *吞吐量* 高，不是「端到端延迟更低」。Kafka 用 *批量 + 顺序* 换吞吐，攒批会带来几毫秒级延迟；RabbitMQ 在单条、小流量、实时投递场景的延迟反而更低。二者是设计目标不同，不是简单的快慢之分。

==== 存储模型：追加日志 vs 队列状态机

- *Kafka*：分区是不可变的 *append-only 日志*，只在文件尾追加，纯顺序写；消息不会因为被消费就删除（按时间/大小整体过期），消费按 offset 顺序读，也是顺序 I/O，几乎没有随机读写。
- *RabbitMQ*：队列要维护 *每条消息* 的状态（ready → delivered/unacked → 待删除），投递要标记、ack 后要删除，队列索引与元数据频繁更新，随机读写 + 锁竞争；消息堆积时索引膨胀，性能下降明显。
- 类比：Kafka 像不停追加写日志文件，RabbitMQ 像维护一张不断增删改的表。

==== 零拷贝与页缓存

- *Kafka*：写入先落 OS *page cache*（异步刷盘），读大概率命中缓存 ≈ 读内存；消费时用 `sendfile` 把页缓存里的数据 *从内核态直接发到 socket*，跳过「内核 → 用户 → 内核」的两次拷贝与上下文切换。Broker 不解析消息体、只做搬运，也绕开了 JVM 堆与 GC 压力。
- *RabbitMQ*：消息需从存储读出、经 Erlang 进程处理、再序列化写入 socket，数据在用户态完整走一遍，每条都有编解码与内存拷贝开销。

==== 批量贯穿全链路

- 生产者攒批（`batch.size` / `linger.ms`）→ Broker 批量追加与刷盘 → 消费者批量拉取（`fetch.min.bytes` / `max.poll.records`）→ 端到端批量压缩（lz4 / snappy / zstd / gzip）。
- *一次系统调用、一次磁盘 I/O 服务成百上千条消息*，把每条消息的固定成本摊薄到极低。
- RabbitMQ 以 *单条消息* 为路由、投递、confirm、ack 的单位，per-message 开销无法被摊薄。

==== 消费模型：pull + offset vs push + 逐条 ack

- *Kafka* 消费者主动 pull，按 offset 顺序批量取；Broker 只需记录一个位移（`__consumer_offsets`），*不跟踪每条消息的投递状态*；消息可被多个消费组反复读取而互不影响。
- *RabbitMQ* 是 push，Broker 要为每条消息维护 delivery tag、unacked 状态、requeue、confirm 与 prefetch 流控，是一个完整的 *逐条状态机*。

==== 分区并行 vs 单队列串行

- *Kafka*：一个 Topic 拆成多个 Partition 分布到不同 Broker，生产与消费天然并行，加分区/加 Broker 即可水平扩展；消费组内分区与消费者一一对应。
- *RabbitMQ*：单个队列由 *单个 master 节点* 负责（为保证顺序），多消费者只是竞争同一个队列，吞吐受单队列/单节点上限约束；镜像/仲裁队列还要跨节点复制，进一步拉低吞吐。

==== 功能取舍：Kafka 主动「不做」的事

- 不做 Exchange / binding 复杂路由、不做通配符匹配、不做单条 ack 与 reject、不做原生延迟/优先级队列、不做 per-message TTL、不保证全局有序（仅分区内有序）、不做复杂重试与死信（交给应用层）。
- 每一项「不做」都缩短了消息路径。RabbitMQ 作为通用 AMQP broker 把这些能力都实现了，功能更强，成本自然更高。

==== 结论与选型对照

[cols="2,3,3"]
|===
| 维度 | Kafka | RabbitMQ
| 优化目标 | 吞吐 / 日志流 / 可重放 | 路由灵活性与可靠性 / 低延迟
| 消息粒度 | 批量 | 单条
| 存储 | append-only 日志、顺序读写 | 队列 + 状态与索引、随机读写
| 消费 | pull + offset | push + 逐条 ack
| 并行 | 多分区、多 Broker 水平扩展 | 单队列串行，靠多队列分摊
| 典型吞吐 | 十万~百万级 TPS 量级 | 万级 TPS 量级
| 延迟 | 几 ms~几十 ms（攒批带来） | 单条可到 ms 甚至更低
| 适用 | 日志 / 埋点 / 流处理 / 事件溯源 | 业务消息、复杂路由、企业级 AMQP
|===

NOTE: 表中只是数量级参考，实际取决于硬件、`acks`、刷盘策略、消息大小、副本数与压测方式；当要求 `acks=all` + 同步刷盘 + 单条小消息时，Kafka 的优势会明显缩小。

*一句话总结*：Kafka 把消息系统「退化」成一条高吞吐的顺序日志管道，用 *顺序 I/O、页缓存零拷贝、全链路批量、分区并行、极简的逐条状态管理* 把每条消息的成本压到最低；RabbitMQ 把每条消息当成需要独立路由与确认的对象，功能更强但路径更长。

反过来别答错：若面试官问「哪个延迟更低」，要说清 RabbitMQ 在单条实时投递上可能更低，Kafka 强在 *吞吐与可重放*。

=== Kafka 核心

- 组成：Producer / Consumer / Broker / Topic / Partition / Consumer Group。
- 分区：顺序写追加日志，`offset` 定位；分区内有序。
- 副本：Leader/Follower，`ISR` 同步副本集合，`acks=0/1/all`。
- 高吞吐：顺序写磁盘、页缓存、零拷贝（`sendfile`）、批量压缩、分区并行。
- 消费：消费组内一个分区只被一个消费者消费；`__consumer_offsets` 存位移。
- 可靠性：`acks=all` + 幂等（`enable.idempotence`）+ 事务保证 exactly-once。
- 数据保留：按时间/大小，`segment` 分段，可重读。

=== RocketMQ 核心

- 组成：NameServer（路由）、Broker（存储）、Producer、Consumer。
- 存储：`CommitLog` 顺序写 + `ConsumeQueue` 索引 + `IndexFile`。
- 消息类型：普通、顺序（`MessageQueueSelector` + 局部锁）、延迟（18 个延迟级别）、事务（半消息 + 回查）。
- 事务消息：半消息 → 本地事务 → commit/rollback，Broker 定时回查。
- 重复消费：天然至少一次，需幂等（业务唯一键 / 状态表）。

=== 消息可靠性三问题

- *丢失*：生产端（确认/重试）、Broker（持久化+副本）、消费端（先消费后提交 offset / 手动 ack）。
- *重复*：幂等设计（唯一键去重、状态机、乐观锁）。
- *顺序*：同一业务 key 路由到同一分区/队列；局部有序。

=== RabbitMQ 核心

==== 核心概念与消息流转

- 组件：Producer → *Exchange*（交换机）→ *Binding*（绑定关系）→ *Queue* → Consumer；Connection 之上复用多个轻量 *Channel*，Virtual Host 做逻辑隔离。
- 流转：生产者把消息发给 Exchange 并带上一个 `routing key`；Exchange 按「*自身类型 + routing key + binding key*」决定投递到哪些队列；*消费者只从队列取消息，完全不感知 Exchange 与 routing key*。
- 两个关键区别：
  - *一个队列挂多个消费者 = 竞争消费*：一条消息只会被其中一个消费者拿到（默认轮询，可用 `prefetch` 调节）。
  - *多个队列绑定同一 Exchange = 每个队列各拿到一份拷贝*：这是「发布订阅」与「工作队列」的根本区别。
- 若消息发到 Exchange 却 *没有任何队列匹配*，默认直接丢弃；可用 `mandatory=true` + Return 回调，或配置 *备份交换机 Alternate Exchange* 兜底。

==== 四种 Exchange 与 routing key 的作用

`routing key` 是生产者发送消息时附带的一个字符串（AMQP 0-9-1 中上限 255 字节），是 Exchange 做路由决策的依据（headers 类型除外）。不同 Exchange 对它的处理完全不同：

[cols="1,2,3,2"]
|===
| Exchange 类型 | 对 routing key | 匹配规则 | 典型场景
| `direct` | 使用 | routing key 与 binding key *完全相等* 才投递 | 按日志级别 / 业务类型精确分流
| `fanout` | *忽略* | 不做比较，广播到所有绑定队列 | 广播通知、缓存清理、配置变更
| `topic` | 使用 | 按 `.` 分词，`*` 匹配一个词，`#` 匹配零到多个词 | 分类订阅、多维路由
| `headers` | *忽略* | 用消息 headers 属性匹配，`x-match=all`（全部匹配）或 `any`（任一匹配） | 按属性而非 key 路由，性能较差、较少使用
|===

- *默认交换机*：名字是空字符串 `""`，行为相当于 direct，每个队列会自动以「队列名」作为 binding key 绑定它。简单模式与工作队列模式走的就是它，此时 `routing key` 必须 *等于队列名*。
- 一个队列可以用 *多个 binding key* 绑定到同一个 Exchange；一条消息也可能同时匹配多个队列，从而被投递多份。
- topic 通配符示例（`routing key = order.paid.vip`）：
  - `order.*.vip` ✓（`*` 恰好一个词）
  - `order.#` ✓（`#` 零到多个词）
  - `#.vip` ✓
  - `order.*` ✗（三段不能匹配两段）
  - 单词以 `.` 分隔，`*` 不能匹配半个词；`*` 与 `#` 只能出现在分词位置。

==== routing key 与 binding key 的区别（易混）

- *routing key*：属于 *消息*，生产者发送时指定，一条消息只有一个。
- *binding key*：属于 *绑定关系*，队列绑定到 Exchange 时指定，一个队列可以有多个（topic 里就是通配符模式）。
- Exchange 拿「消息的 routing key」去匹配「各队列的 binding key」；`fanout` / `headers` 下两者都不参与匹配（binding key 通常写空串）。
- 一句话记：*key 跟着消息走，binding key 写在绑定关系上*。

==== 六种工作模式

1. *简单模式 Simple（Hello World）*
   - 一个生产者 → 默认交换机 → 一个队列 → 一个消费者；`routing key` 填队列名，无需显式声明 Exchange 与 Binding。
   - 生产很少直接用，主要用于理解模型。

2. *工作队列 Work Queues（竞争消费者）*
   - 一个队列挂多个消费者，一条消息 *只被一个消费者* 消费，默认轮询分发（round-robin）。
   - 用 `basicQos(prefetchCount=1)` + 手动 ack 实现「能者多劳」，避免慢消费者堆积、快消费者空闲。
   - 场景：耗时任务分发（发邮件、生成报表、图片处理）、削峰。

3. *发布订阅 Publish/Subscribe（fanout）*
   - Exchange 为 `fanout`，*忽略 routing key*，消息广播到所有绑定队列；每个消费者有自己的队列，各拿到一份完整拷贝。
   - 场景：一个事件多方消费（下单后同时通知库存、积分、短信、审计）。

4. *路由模式 Routing（direct）*
   - Exchange 为 `direct`，routing key 与 binding key *精确相等* 才投递。
   - 例：队列 A 绑 `error`、队列 B 绑 `info` 与 `warn`；发 `error` 只进 A，发 `info` 只进 B。
   - 场景：按级别 / 类型分流，不同消费者处理不同类别消息。

5. *主题模式 Topics（topic）*
   - Exchange 为 `topic`，用通配符做模糊匹配，是 direct 的增强。
   - 例：`log.#` 收全部日志，`log.*.order` 收订单模块各级别日志。
   - 场景：多维分类订阅，消费者只关心某类消息的子集。

6. *RPC 模式*
   - 客户端发消息时带 `reply_to`（回调队列名）与 `correlation_id`（请求唯一标识）；服务端处理后把结果发到 `reply_to` 队列并原样带回 `correlation_id`，客户端据此匹配响应。
   - 注意：RabbitMQ *不内置*请求-响应语义，这是靠两个队列 + 消息属性约定模拟的；生产更常用 HTTP/gRPC，了解原理即可。

补充：官方教程还有 *Publisher Confirms*，属于可靠性机制而非工作模式——生产者开启 confirm，Broker 落盘后回 ack，未确认则重试，是「消息不丢」的关键一环。

==== 工作模式速查表

[cols="2,1,2,2,2"]
|===
| 模式 | Exchange | routing key | 一条消息给几个消费者 | 典型场景
| 简单模式 | 默认 `""` | 队列名 | 1 | 入门 / 单点对点
| 工作队列 | 默认 `""` | 队列名 | 1（多消费者竞争） | 耗时任务分发、削峰
| 发布订阅 | `fanout` | 忽略 | 每个队列各一份 | 事件广播、多方消费
| 路由模式 | `direct` | 精确匹配 | 匹配上的队列各一份 | 按级别 / 类型分流
| 主题模式 | `topic` | 通配符匹配 | 匹配上的队列各一份 | 多维分类订阅
| RPC | 默认 / `direct` | 队列名 | 1 | 请求-响应（少用）
|===

==== 可靠性与路由相关注意点

- *持久化三件套*：Exchange 声明 durable、Queue 声明 durable、消息 `deliveryMode=2`，缺一个重启都可能丢消息。
- *生产者 confirm* + *消费者手动 ack*：ack 必须在业务处理成功之后；`prefetch` 限制单个消费者未 ack 的消息数，防止囤积。
- *无匹配队列*：`mandatory=true` + ReturnListener 感知不可路由消息，或用 Alternate Exchange 统一收集，避免静默丢弃。
- *死信队列 DLX*：来源是消息被 `reject/nack` 且不 requeue、TTL 过期、队列达到长度上限；配合 `x-dead-letter-exchange` 与 `x-dead-letter-routing-key` 转发。
- *延迟队列*：TTL + DLX，或 `rabbitmq-delayed-message-exchange` 插件；注意 TTL + DLX 方案在队列头部消息未过期时会阻塞后面的消息。

=== 如何保证消息不丢、不重、有序

1. 不丢：生产确认 + Broker 持久化 + 消费手动确认（ack 时机在业务成功之后）。
2. 不重：业务幂等（数据库唯一索引、Redis setnx、状态机）。
3. 有序：分区/队列内有序，单 key 路由同一分区，消费端单线程或加锁。

== ZooKeeper / 分布式协调

- 数据模型：树形 ZNode（持久/临时/顺序节点）。
- 用途：配置中心、命名服务、分布式锁、选主、注册中心（Dubbo 早期）。
- 一致性：ZAB 协议，过半写入成功即成功，保证顺序一致。
- 分布式锁：临时顺序节点，最小序号获得锁，监听前一节点；或 `curator` 封装。
- 会话：心跳维持，临时节点随会话失效自动删除。
- 注册中心对比：ZooKeeper（CP）vs Eureka（AP）vs Nacos（AP+CP 可切换）。

== Elasticsearch

- 倒排索引：词项 → 文档列表，全文检索核心。
- 架构：Index → Shard（主分片 + 副本），节点角色（master/data/coordinate/ingest）。
- 写入：refresh（默认 1s 可见）、translog（WAL 防丢失）、flush（落 Lucene segment）。
- 查询：query（评分）与 filter（缓存不评分）；`bool` 组合 must/should/must_not。
- 与关系库对比：ES 不适合事务与频繁更新，适合检索/聚合/日志。
- 深度分页：`from+size` 有性能问题，用 `search_after` 或 scroll。

== Netty

- 基于 NIO，`EventLoop`（单线程事件循环）+ `Channel` + `ChannelHandler` + `ByteBuf`。
- Reactor 模型：主从 Reactor，BossGroup 处理连接，WorkerGroup 处理读写。
- 零拷贝：`CompositeByteBuf`、`FileRegion.transferTo`、直接内存。
- 解决粘包/拆包：`DelimiterBasedFrameDecoder`、`LengthFieldBasedFrameDecoder`、`FixedLengthFrameDecoder`。

== Nginx

- 反向代理、负载均衡、静态资源、动静分离、限流。
- 负载均衡策略：轮询、加权轮询、`ip_hash`、`least_conn`、`fair/url_hash`（需模块）。
- 高并发：Master-Worker 多进程、epoll 多路复用。

== 各中间件擅长领域与注意点

=== Redis

- *擅长领域*：缓存、分布式锁、排行榜（ZSet）、计数器、限流、去重（Set/布隆过滤器）、Session 共享、发布订阅、延时队列（ZSet/Stream）。
- *注意点*：
  - 纯内存，容量受内存限制，大 value 拖慢网络与内存效率。
  - 持久化（RDB/AOF）存在数据丢失窗口，不能作为唯一数据源。
  - 集群下多 key / 跨槽操作受限，需用 hash tag 保证同槽。
  - 大 key、热 key 会打爆单节点，需拆分或本地缓存兜底。
  - 单命令原子，多命令需 Lua 或事务保证原子。

=== Kafka

- *擅长领域*：高吞吐日志/事件流、大数据管道、消息可重放/审计、流式计算（配合 Flink/Spark）、削峰解耦。
- *注意点*：
  - 攒批导致延迟偏高，不适合低延迟即时场景。
  - 仅分区内有序，全局无序。
  - 位移提交与重复消费需业务幂等兜底。
  - 传统版本依赖 ZooKeeper（新版本 KRaft 已可去 ZK）。

=== RocketMQ

- *擅长领域*：金融级消息、事务消息（半消息）、顺序消息、延迟消息、大规模业务消息（阿里生态）。
- *注意点*：
  - 组件较多（NameServer/Broker），运维成本较高。
  - 至少一次投递，需业务幂等。
  - 延迟消息为固定级别，不够灵活。

=== RabbitMQ

- *擅长领域*：灵活路由（direct/fanout/topic）、企业级、低延迟、标准 AMQP 协议、与多语言互通。
- *注意点*：
  - 吞吐相对低，不适合超大流量。
  - 集群/镜像队列/持久化配置复杂，Erlang 语言运维门槛高。

=== ZooKeeper

- *擅长领域*：分布式协调（配置中心、命名服务、选主、分布式锁）、强一致元数据。
- *注意点*：
  - 不适合存大数据，znode 不宜过大、数量不宜过多。
  - 是 CP 系统，网络分区时可能短暂不可用。
  - 写性能有限，适合读多写少。

=== Elasticsearch

- *擅长领域*：全文检索、日志分析、聚合统计、时序数据检索与可视化（ELK）。
- *注意点*：
  - 不适合事务与频繁更新（写放大、段合并开销）。
  - 近实时（refresh 默认 1s），非强一致。
  - 内存/CPU 消耗大，需 JVM 与分片调优；深分页性能差。

=== Netty

- *擅长领域*：高性能网络通信、网关、RPC 框架底层、长连接推送。
- *注意点*：
  - 需处理粘包/拆包。
  - `ByteBuf` 引用计数易导致内存泄漏，需正确 release。
  - 需理解 EventLoop 线程模型，避免阻塞事件循环。

=== Nginx

- *擅长领域*：反向代理、负载均衡、静态资源、限流、动静分离。
- *注意点*：
  - 动态内容需转发后端；健康检查与复杂 LB 依赖第三方模块/商业版。
  - 配置变更需 reload，注意平滑升级。

== 高频真题与参考答案

=== 1. Redis 有哪些数据结构？底层实现？

- String（SDS，int/embstr/raw）、List（quicklist）、Hash（ziplist/hashtable）、Set（intset/hashtable）、ZSet（skiplist + dict）。
- 另有大类：Bitmap、HyperLogLog、GEO、Stream。

=== 2. RDB 与 AOF 的区别？如何选择？

- RDB：二进制快照，恢复快、文件小，但可能丢最近数据；适合备份/冷备。
- AOF：追加命令日志，数据更完整，`everysec` 最多丢 1 秒；文件大、恢复慢，可重写压缩。
- 选择：对数据完整性要求高用 AOF（或混合持久化）；做备份、能容忍少量丢失用 RDB；生产常「RDB + AOF 混合」。

=== 3. 缓存穿透、击穿、雪崩分别是什么？如何解决？

- 穿透：查不存在数据直达 DB → 缓存空值（短 TTL）+ 布隆过滤器。
- 击穿：热点 key 失效瞬间打爆 DB → 互斥锁重建、逻辑过期 + 后台刷新。
- 雪崩：大量 key 同时失效或 Redis 宕机 → TTL 加随机值、多级缓存、集群高可用、限流降级。

=== 4. 缓存与数据库一致性如何保证？

- 推荐「先更 DB 再删缓存」；延迟双删兜底；订阅 binlog（Canal）异步删除。
- 本质是最终一致；强一致需分布式锁/版本号。写多读少或强一致场景慎用缓存。

=== 5. Redis 为什么快？6.0 多线程是什么？

- 快：纯内存、单线程无锁切换、I/O 多路复用（epoll）、高效数据结构、命令原子。
- 6.0 多线程：仅网络 I/O 读写（解析/回写 socket）多线程化，命令执行仍是单线程，保证原子性。

=== 6. 用 Redis 实现分布式锁，注意哪些问题？

- 加锁：`SET key token NX EX`（原子）。
- 释放：Lua 脚本「比对 token 再删除」，防误删他人锁。
- 续期：业务超时需看门狗（Redisson）自动续期。
- 其它：可重入、可重试、主从切换时锁丢失风险（RedLock 或 ZK/etcd 增强）。

=== 7. Kafka 为什么吞吐高？如何保证消息不丢/不重复？

- 吞吐高：顺序写磁盘、页缓存、零拷贝（sendfile）、批量+压缩、分区并行。
- 不丢：`acks=all` + 足够副本 + 幂等（`enable.idempotence`）+ 消费端处理成功再提交位移。
- 不重复：本身至少一次，靠业务幂等（唯一键、状态表）去重。

=== 8. RocketMQ 事务消息原理？延迟消息如何实现？

- 事务消息：发半消息（不可见）→ 执行本地事务 → 回执 commit/rollback；未回执时 Broker 定时回查本地事务状态，最终确定投递。
- 延迟消息：Broker 内置 18 个延迟级别（如 1s/5s/10s/30s/1m...），消息先存延迟队列，到时间再投递。

=== 9. 消息顺序消费如何保证？

- 生产端：同一业务 key 路由到同一分区/队列（`MessageQueueSelector`）。
- 消费端：分区内天然有序，消费端单线程处理或加锁，保证局部有序。
- 强调：是「局部有序」而非全局有序。

=== 10. ZooKeeper 如何实现分布式锁与选主？

- 分布式锁：创建临时顺序节点，序号最小者获得锁，其余监听前一个节点，释放/会话断开则自动删除并唤醒后继。
- 选主：同样用临时顺序节点，最小序号当选；或利用 leader 选举 API（如 Curator `LeaderLatch`）。

=== 11. ES 的倒排索引与写入流程？

- 倒排索引：分词后建立「词项 → 文档 ID 列表」映射，配合词频/位置信息，实现快速全文检索。
- 写入流程：写入内存 buffer + translog（WAL）→ refresh（1s）生成 segment 可搜索 → 定期 flush 落盘 Lucene segment，后台段合并。

=== 12. Netty 的线程模型与零拷贝？

- 线程模型：主从 Reactor，BossGroup 处理连接、WorkerGroup 处理读写，一个 EventLoop 绑定一个线程循环处理多个 Channel。
- 零拷贝：`CompositeByteBuf` 合并、`FileRegion.transferTo`（sendfile）、直接内存避免堆拷贝。

=== 13. Kafka 与 RocketMQ 如何选型？

- 大数据/日志/流式、超高吞吐 → Kafka。
- 金融级事务消息、顺序/延迟消息、Java 生态业务消息 → RocketMQ。
- 通用企业、灵活路由、低延迟小流量 → RabbitMQ。

=== 14. 如何设计一个消息队列？

- 存储：顺序写日志（CommitLog）+ 索引（分区/队列）。
- 路由：NameServer/元数据 + 分区 hash 路由。
- 可靠性：持久化 + 副本 + 生产确认 + 消费确认。
- 高可用：主从复制 + 自动故障转移。
- 功能：顺序、延迟、事务、重试、死信、幂等。
- 性能：批量、压缩、零拷贝、异步刷盘。

=== 15. 为什么 Kafka 比 RabbitMQ 快？

- *先纠正前提*：准确说是 *吞吐量* 高，不是延迟更低。Kafka 用批量和顺序换吞吐，攒批带来几毫秒延迟；RabbitMQ 在单条、小流量、实时投递场景延迟反而更低。
- *存储*：Kafka 分区是 append-only 日志，纯顺序写、按 offset 顺序读、消费不删单条消息；RabbitMQ 队列要维护每条消息状态（ready/unacked/删除）与队列索引，随机读写、堆积时索引膨胀。
- *I/O*：Kafka 写落 OS page cache、消费用 `sendfile` 零拷贝从内核直接发 socket，Broker 不解析消息体、绕开 JVM GC；RabbitMQ 消息要经 Erlang 进程读出、序列化，数据完整走一遍用户态。
- *批量*：生产者攒批、Broker 批量刷盘、消费者批量拉取、端到端压缩，一次 I/O 服务成百上千条；RabbitMQ 以单条消息为路由/confirm/ack 单位，固定成本无法摊薄。
- *消费模型*：Kafka pull + 只记录 offset，不跟踪每条消息状态；RabbitMQ push + 逐条 delivery tag、unacked、requeue、prefetch 流控。
- *并行*：Kafka 多 Partition 分布多 Broker 天然水平扩展；RabbitMQ 单队列由单个 master 串行负责，多消费者只是竞争同一队列。
- *功能取舍*：Kafka 不做复杂 Exchange 路由、单条 ack、原生延迟/优先级队列、全局有序、复杂重试与死信，路径更短；RabbitMQ 功能全面但每一步都要成本。
- *结论*：Kafka 强在吞吐与可重放（日志/埋点/流处理），RabbitMQ 强在路由灵活、单条可靠性与低延迟（业务消息）。具体拆解见「为什么 Kafka 吞吐远高于 RabbitMQ」。
