本手册面向 Java 后端面试的「基础」部分，覆盖语法特性、面向对象、核心类库与 JVM 入门。建议配合真题练习。

== 语言基础

=== 基本数据类型与包装类

Java 有 8 种基本数据类型：`byte`(1) / `short`(2) / `int`(4) / `long`(8) / `float`(4) / `double`(8) / `char`(2) / `boolean`(1 位)。

- 包装类：`Byte/Short/Integer/Long/Float/Double/Character/Boolean`。
- 装箱与拆箱：基本类型与包装类之间自动转换，本质是编译器调用 `valueOf()` 与 `xxxValue()`。
- 缓存：`Integer` 默认缓存 `-128~127`（`IntegerCache`），`Boolean/Byte/Short/Character` 全量缓存，`Long` 缓存 `-128~127`。故 `Integer.valueOf(100) == Integer.valueOf(100)` 为 `true`，`new Integer(100)` 则不同。
- 比较：包装类之间比较用 `equals`，与基本类型用 `==` 时自动拆箱，注意 `null` 拆箱会 NPE。

.常见陷阱
[source,java]
----
Integer a = 200, b = 200;
a == b;          // false（超出缓存范围）
Integer c = 100, d = 100;
c == d;          // true（命中缓存）
Integer e = null;
int f = e;       // 拆箱抛 NullPointerException
----

=== == 与 equals / hashCode

- `==`：基本类型比「值」，引用类型比「地址」。
- `equals`：`Object` 默认实现就是 `==`，子类（如 `String`、集合）重写为比「内容」。
- 契约：重写 `equals` 必须同时重写 `hashCode`——相等对象 `hashCode` 必相等；反之 `hashCode` 相等不代表对象相等。
- 经典应用：`HashMap` 先按 `hashCode` 定位桶，再按 `equals` 判等。

=== String / StringBuilder / StringBuffer

- `String` 不可变（`final char[]/byte[]`），每次拼接产生新对象。
- `StringBuilder` 可变、线程不安全、性能好。
- `StringBuffer` 可变、方法 `synchronized`、线程安全、性能差。
- `+` 拼接在编译期/运行期会优化为 `StringBuilder`（常量拼接直接常量折叠），循环内拼接应显式用 `StringBuilder`。
- 常量池：字面量进入运行时常量池，`String.intern()` 可将对象放入常量池并返回引用。

=== 值传递还是引用传递

Java 只有「值传递」：基本类型传值副本，引用类型传「引用地址的副本」。因此方法内修改引用指向的「对象内容」会生效，但修改引用「指向」本身不会影响外部。

[source,java]
----
void change(Person p) {
    p.setName("B");   // 生效：改了对象内容
    p = new Person(); // 无效：改了副本引用
}
----

== 面向对象

=== 三大特性

- *封装*：隐藏内部实现，通过访问控制（`private/protected/public/default`）暴露接口。
- *继承*：子类复用父类，`extends` 单继承，接口 `implements` 多实现。
- *多态*：父类引用指向子类对象，运行时动态绑定方法（虚方法分派），接口与实现解耦的基础。

=== 重写（Override）与重载（Overload）

- 重写：子类重定义父类方法，方法签名相同，返回类型可为子类型（协变返回），访问权限不能更窄，异常不能更宽；`@Override` 校验。
- 重载：同类中方法名相同、参数列表不同，与返回类型无关，编译期决定。

=== 接口与抽象类

[cols="1,2,2"]
|===
| 对比项 | 接口 | 抽象类
| 关键字 | `interface` | `abstract class`
| 继承 | 可实现多个 | 只能单继承
| 方法 | 默认 public abstract（可 default/static/private） | 可有抽象与具体方法
| 字段 | 仅 `public static final` 常量 | 可有实例变量
| 构造器 | 无 | 有
| 定位 | 定义能力/契约（has-a） | 抽取共性（is-a）
|===

=== 关键字与修饰符

- `final`：修饰类不可继承、方法不可重写、变量不可变（引用不可变，对象内容可变）。
- `static`：类级别共享，随类加载初始化，方法内不能访问实例成员。
- `transient`：字段不参与序列化。
- `volatile`：保证可见性与禁止重排序，不保证原子性（详见进阶篇）。
- `synchronized`：互斥锁，保证原子性/可见性/有序性（详见进阶篇）。

== 异常体系

=== 继承结构

`Throwable` 分两支：

- `Error`：JVM 级错误（`OutOfMemoryError`、`StackOverflowError`），通常不捕获。
- `Exception`：分受检异常 `CheckedException`（编译期强制处理，如 `IOException`）与非受检 `RuntimeException`（如 `NullPointerException`、`IndexOutOfBoundsException`）。

=== 异常处理原则

- `try-catch-finally`：`finally` 必执行（`System.exit` 除外），`return` 在 `finally` 前求值。
- 多个 `catch` 按顺序匹配，子类在前。
- `try-with-resources`（JDK7+）：实现 `AutoCloseable` 的资源自动关闭，异常压制机制。
- 捕获异常尽量具体，避免吞异常、避免 `catch (Exception e) {}` 空处理。

[source,java]
----
try (BufferedReader br = Files.newBufferedReader(path)) {
    return br.readLine();
} // 自动 close
----

=== try-catch-finally 注意事项

NOTE: 与 `try` 搭配的是 *finally* 而不是 `final`；`final` 是修饰符（类不可继承、方法不可重写、变量引用不可变），`finalize()` 是已废弃的 `Object` 方法，三者不要混淆（详见真题第 8 题）。

==== finally 的执行时机与返回值陷阱

- 顺序：try 中 `return` 的表达式 *先求值并暂存*，再执行 `finally`，最后才真正返回；所以 `finally` 夹在「return 求值之后、返回之前」。
- *禁止在 finally 中 `return`*：会覆盖 try/catch 的返回值，还会吞掉 try 中抛出的异常。
- *禁止在 finally 中抛异常*：会覆盖 try/catch 的原始异常，导致真正的错误丢失。
- 改返回值的差异：基本类型（或给引用重新赋值）不影响返回结果，但修改 *引用对象的内容* 会反映到返回对象上。

[source,java]
----
static int f1() {
    int x = 1;
    try { return x; }       // 返回值 1 已确定
    finally { x = 2; }      // 返回的仍是 1
}

static List<String> f2() {
    List<String> list = new ArrayList<>();
    try { return list; }
    finally { list.add("x"); }   // 返回的 list 中能看到 "x"
}
----

==== finally 并非绝对执行

- 以下情况不会（或来不及）执行：`System.exit()`、JVM 崩溃/进程被强杀、断电、try 块内死循环、线程被强制终止。
- 守护线程在所有非守护线程结束时会直接被 JVM 终止，`finally` 可能来不及跑。
- 结论：`finally` 只适合清理「本次调用」的资源（关流、解锁、还原标志位），*不要把持久化、发消息、状态落库等关键业务放进 finally 求「保底」*。

==== 资源关闭优先用 try-with-resources

- 手写 `finally` 关流容易漏判空、多个资源关闭繁琐，且 `close()` 自身抛异常会 *覆盖业务异常*。
- `try-with-resources`（JDK7+）自动关闭实现了 `AutoCloseable` 的资源：多个资源按 *声明的逆序* 关闭；`close()` 抛出的异常作为 *suppressed 异常* 挂在主异常上，不会丢失。

[source,java]
----
try (InputStream in = new FileInputStream(src);
     OutputStream out = new FileOutputStream(dst)) {
    in.transferTo(out);
} // 先关 out，再关 in；close 异常以 suppressed 形式保留
----

- 若必须手写，注意逐层判空并单独处理 `close()` 的异常，或用 `IOUtils.closeQuietly` 之类的工具方法。

==== catch 的匹配与顺序

- 多个 `catch` 自上而下匹配，*子类必须写在父类之前*，否则编译报错（不可达的 catch 块）。
- JDK7+ 支持多异常合并 `catch (IOException | SQLException e)`，此时异常变量隐式 `final`，且并列类型之间不能有继承关系。
- 避免 `catch (Exception e)` 一网打尽，更不要 `catch (Throwable)` —— 会把 `OutOfMemoryError` 这类 `Error` 一并吞掉，掩盖 JVM 级故障。

==== 不要吞异常 / 正确记录日志

- 空 `catch` 块、只调用 `e.printStackTrace()` 都是大忌：`printStackTrace` 输出到标准错误流，日志系统采集不到，也丢失业务上下文。
- 正确做法：用日志框架带上上下文记录（`log.error("扣款失败, orderId={}", orderId, e)`）→ 包装后重抛，或转换为明确的业务错误码。
- 重抛要保留原始堆栈：`throw e;`；包装时务必把原异常作为 cause 传入 `new XxxException("...", e)`；不要 `throw new RuntimeException(e.getMessage())`，会丢掉堆栈和异常类型。

==== 受检异常与 @Transactional 的高频坑

- Spring `@Transactional` 默认只对 `RuntimeException` / `Error` 回滚，受检异常不回滚（需 `@Transactional(rollbackFor = Exception.class)`）。
- 更常见的线上事故：在事务方法内 `try-catch` 吞掉异常又不重新抛出，事务拦截器收不到异常 → *事务照样提交，不回滚*。
- 既要记日志又要回滚：处理完把异常 `throw` 出去，或调用 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。

==== 性能与编码习惯

- `try-catch` 本身开销很小，昂贵的是「抛出异常」时填充堆栈（`fillInStackTrace`）；因此 *不要用异常做正常流程控制*（拿异常跳出循环、用异常表示业务分支）。
- `try` 块只包住真正可能抛异常的最小代码段，便于定位，也能缩小锁与事务的范围。
- 异常信息带业务上下文（订单号、用户 ID），但不要把密码、密钥、身份证号等敏感数据写进日志。
- 自定义异常优先继承 `RuntimeException`，避免受检异常层层声明污染接口签名。
- `finally` 里只做轻量清理，不放业务逻辑、不做远程调用。

==== 受检 vs 非受检怎么选

- *受检异常*：调用方可以合理恢复的情况（文件不存在、网络超时需重试）→ 编译期强制处理。
- *非受检异常*：编程错误或不可恢复（NPE、下标越界、状态非法）→ 快速失败，不必层层声明。
- 现代框架（Spring、MyBatis）普遍倾向非受检异常，业务代码更清爽。

== 集合框架（速览，进阶详见集合专题）

- `List`：`ArrayList`（数组，随机访问快）、`LinkedList`（链表，增删快）、`Vector`（线程安全已过时）。
- `Set`：`HashSet`（哈希无序）、`LinkedHashSet`（保序）、`TreeSet`（红黑树有序）。
- `Map`：`HashMap`（哈希）、`LinkedHashMap`（保序）、`TreeMap`（红黑树有序）、`ConcurrentHashMap`（并发安全）、`Hashtable`（过时）。
- `Queue`：`PriorityQueue`（堆）、`ArrayDeque`（双端队列）、`LinkedList` 亦可作队列。

=== 快速选择记忆点

- `HashMap` 默认容量 16、负载因子 0.75、JDK8 后链表转红黑树（长度 ≥ 8 且桶 ≥ 64）。
- `ConcurrentHashMap`：JDK7 分段锁 `Segment`，JDK8 改为 `CAS + synchronized` 锁单个桶节点。
- `ArrayList` 扩容约 1.5 倍，`HashMap` 扩容 2 倍。

== 常用类库与 I/O

=== 泛型

- 编译期类型检查，运行时类型擦除。
- `? extends T`（上界，只读）、`? super T`（下界，只写）、`?` 无界通配。
- PECS 原则：Producer Extends，Consumer Super。

=== 反射

- 运行时获取类信息：`Class.forName()`、`getDeclaredMethods/Fields/Constructors`。
- 动态创建对象、调用方法、访问私有字段（`setAccessible(true)`）。
- 应用：Spring IoC、JDBC 动态代理、序列化框架。

=== 动态代理

- JDK 动态代理：基于接口，`Proxy.newProxyInstance` + `InvocationHandler`。
- CGLIB：基于继承，字节码生成子类，可代理普通类。
- Spring AOP 默认 JDK 代理（有接口时），否则 CGLIB。

=== BIO / NIO / AIO

- BIO：阻塞 I/O，一线程一连接，`InputStream/OutputStream`。
- NIO：非阻塞，`Channel + Buffer + Selector` 多路复用，单线程管理多连接。
- AIO：异步 I/O，回调通知（Java 异步网络编程，实际使用较少）。
- Netty 基于 NIO 封装，是高性能网络框架事实标准（见中间件篇）。

== JVM 入门（深入见进阶篇）

- 内存区域：堆（对象）、虚拟机栈（栈帧/局部变量）、方法区（元空间/常量池）、程序计数器、本地方法栈。
- 垃圾回收：判断可达性（GC Roots），算法有标记-清除、标记-复制、标记-整理；常见收集器 `Serial/Parallel/CMS/G1/ZGC`。
- 类加载：加载→验证→准备→解析→初始化；双亲委派模型。

== JDK 各版本升级点与差异

=== 版本节奏与 LTS

- JDK9 起改为 *每 6 个月一个版本*（每年 3 月、9 月），每 2 年选一个 *LTS*（长期支持）版本：`8 → 11 → 17 → 21 → 25`。
- 非 LTS 版本只维护约 6 个月，生产环境一般只用 LTS。
- 面试高频：说清「8 的 Lambda、17 的强封装、21 的虚拟线程」三个里程碑，再补 LTS 节奏即可。
- 标为「预览 / 孵化」的特性需要 `--enable-preview` 才能使用，且 *不保证下个版本兼容，禁止用于生产*。

=== 四个 LTS 版本详解

==== JDK 8（2014，使用最广的基座）

- *Lambda 与函数式接口*：`@FunctionalInterface`、`java.util.function`（Predicate/Function/Consumer/Supplier）。
- *Stream API*：链式过滤/映射/聚合，支持并行流；方法引用 `Class::method`。
- *新日期时间 API*：`java.time`（`LocalDate` / `LocalDateTime` / `ZonedDateTime` / `Duration` / `DateTimeFormatter`），不可变且线程安全，替代非线程安全的 `SimpleDateFormat` 和难用的 `Date/Calendar`。
- *Optional*：显式表达「可能为空」，减少 NPE。
- *接口增强*：`default` 方法、`static` 方法，让集合框架等老接口可以平滑扩展。
- *JVM 变化*：*永久代 PermGen 移除，改为元空间 Metaspace*（使用本地内存），`-XX:PermSize/MaxPermSize` 失效，缓解 `OOM: PermGen space`。
- *集合与并发*：`HashMap` 链表过长转红黑树、`ConcurrentHashMap` 改为 CAS + synchronized、`CompletableFuture`、`LongAdder`、`StampedLock`、`Base64`。
- 默认 GC：Parallel Scavenge + Parallel Old。

==== JDK 11（2018，第二个 LTS）

- *HttpClient 转正*：`java.net.http.HttpClient`，支持 HTTP/2、WebSocket、同步与异步，替代老旧的 `HttpURLConnection`。
- *移除 Java EE / CORBA 模块*：JAXB、JAX-WS、`@PostConstruct` 等不再内置 → *8 升 11 最常见的编译失败原因*，需显式加依赖。
- *便利方法*：`String.isBlank/lines/strip/repeat`、`Files.readString/writeString`、`Optional.isEmpty()`；`var` 可用于 Lambda 参数。
- *单文件源码启动*：`java Hello.java`，无需先 `javac`。
- *GC 与诊断*：ZGC（实验性，低延迟）、Epsilon GC（无回收，用于性能测试）、JFR 开源；默认 GC 已是 G1（自 JDK9）。
- TLS 1.3 支持。

==== JDK 17（2021，当前主流生产 LTS）

- *密封类转正*：`sealed` / `permits` / `non-sealed`，精确控制哪些类可以继承。
- *switch 模式匹配（预览）*、增强伪随机数生成器 `RandomGenerator`、恢复严格浮点语义。
- *强封装 JDK 内部 API*（JEP 403）：反射访问 `sun.*` 或 `java.lang` 私有成员默认抛 `InaccessibleObjectException`，需要 `--add-opens`。
- *移除*：Applet API、RMI Activation、实验性 AOT/JIT 编译器；*弃用* Security Manager。
- *生态基线*：*Spring Boot 3 / Spring Framework 6 最低要求 JDK 17*，这也是大量项目停在 17 的原因。

==== JDK 21（2023，新一代 LTS）

- *虚拟线程转正*（最重要，见下节）。
- *Sequenced Collections*：`SequencedCollection` / `SequencedSet` / `SequencedMap`，统一 `getFirst/getLast/reversed/addFirst/addLast`，不再为 `LinkedList`/`LinkedHashSet`/`TreeMap` 各记一套 API。
- *Record Patterns 与 switch 模式匹配转正*：`case` 支持类型匹配、`case null` 与 `when` 守卫，配合 `record` 解构，大幅简化分支代码。
- *分代 ZGC*：为新生代/老年代分别回收，进一步降低分配压力下的停顿。
- 字符串模板（预览，后续版本因设计调整暂停预览）、结构化并发、Scoped Values、FFM API、Vector API 仍为预览/孵化。
- 弃用 Windows 32 位 x86 端口、准备限制动态加载 Agent。

*虚拟线程（Project Loom）要点*：

- 由 JVM 调度的轻量线程，M:N 映射到少量平台线程（*载体线程 carrier thread*）；遇到阻塞 IO 时自动卸载，几 MB 内存即可支撑百万级并发。
- 创建方式：`Thread.ofVirtual().start(...)` 或 `Executors.newVirtualThreadPerTaskExecutor()`，仍然沿用原有 `Thread` API，改造成本低。
- 适合 *IO 密集型*（Web 服务、RPC、数据库调用）；*CPU 密集型不会变快*。
- 注意：*不要池化*（每任务一个虚拟线程）；JDK21 中在 `synchronized` 块内阻塞会 *pin* 住载体线程（可用 `ReentrantLock` 缓解，JDK24 起已改善）；避免海量 `ThreadLocal`（每线程一份副本会放大内存）。

=== 跨版本关键差异与升级注意点

[cols="2,3,4"]
|===
| 变化点 | 起始版本 | 影响与应对
| 默认 GC | JDK9 起 G1 取代 Parallel；JDK14 移除 CMS | 老的 `-XX:+UseConcMarkSweepGC` 在新版直接报错，需清理启动脚本
| 内部 API 封装 | JDK9 模块化 → JDK16 默认 deny → JDK17 强封装 | 反射访问 `sun.*` 或 JDK 私有成员失败，改用公开 API，`--add-opens` 只作临时过渡
| Java EE 模块移除 | JDK11 | 补齐 `jaxb-api`、`javax.annotation` 等依赖
| 默认字符集 | JDK18 起统一 UTF-8 | 依赖平台默认编码（如 GBK）的老代码读写文件会乱码，显式指定 `StandardCharsets.UTF_8`
| 内存模型 | JDK8 移除 PermGen | `-XX:PermSize` 失效，改用 `-XX:MetaspaceSize/MaxMetaspaceSize`
| 三方库兼容 | 每个版本 | ASM / CGLIB / ByteBuddy 需支持新 class 版本，否则 `UnsupportedClassVersionError`
| 框架基线 | JDK17 | Spring Boot 3 / Spring Framework 6 要求 17+；Spring Boot 2 可用 8/11/17
| 预览特性 | 各版本 | 需 `--enable-preview`，且与编译版本严格一致、跨版本不保证兼容，禁止用于生产
|===

*class 文件主版本号*：JDK8 = 52、9 = 53、10 = 54、11 = 55，之后每版 +1，17 = 61、21 = 65。看到 `UnsupportedClassVersionError: class file version 61.0 should be 52.0`，含义是「用 JDK8 运行了 JDK17 编译的类」。

*升级检查清单*：

1. 明确目标 LTS：新项目优先 17 或 21；8 → 17 的老系统建议按 8 → 11 → 17 分步升级。
2. 清理失效的 JVM 参数（`PermSize`、CMS、`PrintGCDetails` 改为 `-Xlog:gc*`）。
3. 全量升级依赖：Spring、ASM/CGLIB/ByteBuddy、日志、序列化、字节码增强与 Java Agent。
4. 处理 `IllegalAccessError` / `InaccessibleObjectException`，优先改代码而不是长期靠 `--add-opens`。
5. 显式指定字符集、时区、Locale，避免默认值变化带来行为差异。
6. 回归 GC 与性能：默认收集器变化、Metaspace 与堆外内存、ZGC/虚拟线程相关指标。
7. 全量回归 + 灰度，重点覆盖反射、序列化、加密、日期格式化、动态代理等敏感点。

== 高频真题与参考答案

=== 1. String 为什么设计成不可变？

- *实现*：`String` 是 `final` 类，内部用 `final` 字符数组（JDK9 起为 `byte[]`），且不提供任何修改内容的方法，所有「修改」都返回新对象。
- *原因*：
  1. 线程安全：不可变对象天然线程安全，可被多线程共享。
  2. 常量池复用：字符串常量池可安全复用同一实例，节省内存。
  3. 可作 `HashMap/HashSet` 的 key：hash 值稳定（`hashCode` 可缓存）。
  4. 安全性：防止被篡改（类名、文件路径、网络参数、反射等依赖字符串的场景）。

=== 2. HashMap 的 put/get 流程与哈希冲突如何解决？

- *结构*：数组（桶）+ 链表 + 红黑树（JDK8）。
- *put 流程*：
  1. 计算扰动后的 hash：`(h = key.hashCode()) ^ (h >>> 16)`。
  2. `(n-1) & hash` 定位桶下标。
  3. 桶为空则直接放入；非空则沿链表/红黑树比较（先比 hash，再比 `equals`）。
  4. key 相同则覆盖 value；否则尾插链表，链表长度 ≥ 8 且桶数 ≥ 64 转红黑树。
  5. 超过阈值触发 `resize` 扩容。
- *get 流程*：同样定位桶，再遍历链表或红黑树查找。
- *哈希冲突*：链地址法（链表+红黑树），配合扰动函数让哈希分布更均匀，减少碰撞。

=== 3. ArrayList 与 LinkedList 的区别与适用场景？

- *ArrayList*：底层 `Object[]` 数组，随机访问 O(1)，末尾增删均摊 O(1)，中间插入/删除 O(n)（需 `System.arraycopy` 搬迁）。
- *LinkedList*：双向链表，随机访问 O(n)，头尾增删 O(1)，节点额外存前驱/后继指针、内存开销大。
- *选型*：读多写少用 `ArrayList`（实际业务绝大多数场景）；仅在频繁头尾增删且很少随机访问时才考虑 `LinkedList`。

=== 4. equals 与 == 的区别？重写 equals 为何要重写 hashCode？

- `==`：基本类型比较「值」，引用类型比较「引用地址」。
- `equals`：`Object` 默认实现就是 `==`，`String`/包装类/集合重写为比较「内容」。
- *为何同重写 hashCode*：二者有契约——`equals` 相等的对象 `hashCode` 必须相等。`HashMap/HashSet` 先按 `hashCode` 定位桶，再按 `equals` 判等；若只重写 `equals` 不重写 `hashCode`，两个逻辑相等的对象 hash 不同、落在不同桶，导致无法命中、集合出现「重复」元素。

=== 5. 异常体系有哪些？finally 在 return 前还是后执行？

- `Throwable` → `Error`（JVM 错误，不捕获）+ `Exception`。
- `Exception` → 受检异常 `CheckedException`（编译期强制处理）+ 非受检 `RuntimeException`。
- *finally 时机*：`finally` 在 `return` 表达式「求值之后、真正返回之前」执行；`finally` 里的 `return` 会覆盖 `try` 的 `return`；`finally` 抛异常会覆盖原异常；除 `System.exit()` 或 JVM 崩溃外 `finally` 必执行。

=== 6. 抽象类和接口如何选择？

- *用抽象类*：存在明显的 is-a 继承关系、需共享实例字段/构造器/非 public 方法或状态时。
- *用接口*：定义能力/契约（has-a）、需要多实现、解耦模块时；JDK8+ 支持 `default` 方法。
- *原则*：优先接口、组合优于继承；抽象类用于抽取模板方法。

=== 7. 什么是值传递？Java 参数传递机制是什么？

- Java 只有*值传递*，无引用传递。
- 基本类型：传「值副本」，方法内修改不影响外部。
- 引用类型：传「引用地址的副本」，通过副本可修改指向的*对象内容*（会生效）；但让副本重新指向新对象（`p = new Person()`）不影响外部引用。

=== 8. final、finally、finalize 的区别？

- `final`：关键字，修饰类（不可继承）、方法（不可重写）、变量（不可变）。
- `finally`：异常处理块，保证资源释放/收尾，必执行。
- `finalize()`：`Object` 方法，GC 回收前可能被调用，JDK9 已废弃、不可靠，绝不用它做资源清理。

=== 9. 谈谈反射与动态代理的原理与应用。

- *反射*：运行时获取类的元信息（`Class.forName()`、`getDeclaredMethods/Fields/Constructors`）、动态创建对象、调用方法、访问私有成员（`setAccessible(true)`）。应用：Spring IoC 注入、ORM、序列化。
- *动态代理*：
  - JDK 代理：基于接口，`Proxy.newProxyInstance` + `InvocationHandler`，代理类实现目标接口。
  - CGLIB：基于继承，运行时生成子类，可代理无接口的类。
  - 应用：Spring AOP、RPC 框架、事务/日志/权限切面。

=== 10. BIO、NIO、AIO 的区别？为什么 Netty 用 NIO？

- *BIO*：阻塞 I/O，一个连接一个线程，`InputStream/OutputStream`，连接多时线程开销大。
- *NIO*：非阻塞，`Channel + Buffer + Selector` 多路复用，单线程可管理大量连接。
- *AIO*：异步 I/O，回调/`Future` 通知完成。
- *Netty 选 NIO*：NIO 非阻塞 + 多路复用，高并发下资源消耗低；BIO 线程模型无法支撑海量连接；AIO 在 Linux 上底层用 epoll 模拟、成熟度与可维护性不如 NIO。
