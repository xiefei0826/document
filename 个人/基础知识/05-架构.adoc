架构篇聚焦分布式理论、微服务治理、高并发/高可用设计、常见系统设计方案与权衡。

== 分布式理论

=== CAP

- 一致性（Consistency）、可用性（Availability）、分区容错（Partition tolerance），三者不可兼得，P 必选。
- 实践：CP（ZooKeeper/etcd，强一致牺牲可用）、AP（Eureka，高可用牺牲强一致）。
- 主流是 BASE（Basically Available 基本可用、Soft state 软状态、Eventually consistent 最终一致）。

=== 一致性模型与协议

- 强一致、弱一致、最终一致。
- 2PC（两阶段提交）：同步阻塞、单点、数据不一致风险。
- 3PC：引入超时与预提交，缓解阻塞。
- TCC（Try-Confirm-Cancel）：业务层补偿，`Try` 预留、`Confirm` 确认、`Cancel` 回滚。
- 本地消息表 / 事务消息（RocketMQ 半消息）：最终一致。
- Saga：长事务拆多本地事务 + 补偿。
- Paxos / Raft：分布式共识（多数派），选主与日志复制。

=== 分布式事务选型

- 单库：本地事务。
- 跨库跨服务强一致场景少，多采用最终一致：TCC、Saga、事务消息 + 本地消息表。
- 原则：能用幂等 + 重试 + 补偿解决就不用强一致。

== 分布式 ID

- UUID：无序，索引性能差。
- 数据库号段：批量分配段。
- Redis 自增：简单但依赖 Redis。
- 雪花算法：时间戳 + 机器 ID + 序列号，趋势递增，需处理时钟回拨（拒绝/等待/备用机器位）。

== 分布式锁

- 实现：Redis（`SET NX EX` + Lua 释放 + Redisson 看门狗）、ZooKeeper（临时顺序节点）、etcd（租约 + 事务）。
- 要点：互斥、防误删（唯一 token）、可重入、自动续期、可重试。

== 微服务

=== 拆分原则

- 单一职责、高内聚低耦合、按业务域（DDD 限界上下文）。
- 服务粒度：过细导致分布式复杂度，过粗难维护。

=== 服务治理

- *注册中心*：服务注册与发现（Nacos/Eureka/Consul/etcd）。
- *配置中心*：动态配置（Nacos/Apollo）。
- *网关*：统一入口、鉴权、路由、限流、日志（Spring Cloud Gateway/Kong/Nginx）。
- *负载均衡*：客户端负载（Ribbon/LoadBalancer）、服务端负载（Nginx/LVS）。
- *服务调用*：RPC（Dubbo/gRPC）与 REST（OpenFeign）。

=== 熔断、限流、降级

- 熔断：调用失败率超阈值打开熔断器，快速失败（Sentinel/Resilience4j/Hystrix）。
- 限流：令牌桶、漏桶、滑动窗口；网关/单机限流。
- 降级：非核心功能关闭或走兜底，保核心链路。

=== 链路追踪与可观测性

- 指标（Metrics）：Prometheus + Grafana。
- 日志（Logging）：集中式 ELK/Loki。
- 链路（Tracing）：SkyWalking/Zipkin/Jaeger，分布式 traceId 贯穿。

=== 服务网格

- Service Mesh（Istio/Envoy）：将治理下沉到 sidecar 代理，解耦业务与基础设施。

== 高并发与高可用

=== 高并发

- 水平扩展：无状态服务 + 负载均衡。
- 缓存：本地缓存（Caffeine）+ 分布式缓存（Redis）多级。
- 异步：MQ 削峰、异步化。
- 池化：连接池、线程池。
- 读写分离、分库分表、CDN、静态化。

=== 高可用

- 冗余：多副本、主备、集群。
- 故障转移：健康检查、自动切换。
- 隔离：资源隔离（线程池/信号量）、舱壁隔离。
- 容灾：多机房、异地多活。
- 监控告警 + 应急演练。

=== 幂等

- 定义：同一请求重复执行结果一致。
- 方案：唯一索引（insert）、Redis `setnx`、状态机（非法状态转移拒绝）、token（防重复提交）、悲观锁/乐观锁。

== 常见系统设计

=== 秒杀系统

- 前端：静态化 + CDN、按钮防抖。
- 网关：限流、校验。
- 后端：Redis 预减库存（Lua 原子）+ MQ 异步下单 + 数据库最终扣减。
- 防超卖：Redis `decr` 原子 / Lua 判断；DB 乐观锁兜底。
- 削峰：消息队列缓冲，下单与扣减解耦。
- 防刷：验证码、风控、单用户限购。

=== 短链接系统

- 发号：自增 ID / 雪花 → Base62 编码；或哈希 + 冲突处理。
- 存储：KV（Redis 热数据 + DB 持久）。
- 重定向：301（永久，省请求）/ 302（临时，便于统计）。
- 优化：布隆过滤器防无效查询、缓存热点。

=== 排行榜

- Redis ZSet：`ZADD/ZINCRBY/ZREVRANGE`，支持实时更新与 TopN。
- 大用户量：分片 + 聚合、定时离线计算。

=== 消息推送 / 未读数

- 全量 vs 增量推送、分桶、Redis 计数 + 懒加载、离线消息存储。

=== 限流算法实现

- 固定窗口：简单，边界突刺。
- 滑动窗口：更平滑。
- 漏桶：恒定速率，应对突发差。
- 令牌桶：允许一定突发，`Guava RateLimiter`、Redis + Lua。

== 设计原则与权衡

- 三高（高性能/高可用/高扩展）与成本权衡。
- 一致性 vs 可用性 vs 分区容错。
- 同步 vs 异步、强一致 vs 最终一致。
- 避免过度设计：先满足当前，预留扩展点。
- 稳定优先：缓存、降级、隔离、监控是基本功。

== 高频真题与参考答案

=== 1. 谈谈你对 CAP 和 BASE 的理解？

- CAP：一致性、可用性、分区容错，三者不可兼得，网络分区（P）必选；分区发生时在 C/A 间取舍，CP 如 ZK/etcd、AP 如 Eureka。
- BASE：基本可用、软状态、最终一致，是 AP 的工程折中，允许短暂不一致、通过异步/补偿最终一致。

=== 2. 分布式事务有哪些方案？如何选型？

- 方案：2PC/3PC（强一致）、TCC（Try-Confirm-Cancel）、Saga（补偿）、本地消息表、事务消息（RocketMQ 半消息）。
- 选型：单库用本地事务；跨库跨服务优先最终一致——可回滚业务用 TCC，长事务用 Saga，消息驱动用事务消息 + 本地消息表；能用幂等+重试+补偿就不用强一致。

=== 3. 微服务如何拆分？如何治理？

- 拆分：单一职责、高内聚低耦合、按业务域（DDD 限界上下文），粒度适中避免过度拆分。
- 治理：注册中心（Nacos/Eureka）、配置中心（Nacos/Apollo）、网关（Gateway）、负载均衡、熔断限流降级（Sentinel）、链路追踪（SkyWalking）。

=== 4. 熔断、降级、限流的区别与实现？

- 熔断：下游失败率超阈值打开熔断器快速失败，防雪崩（Sentinel/Resilience4j）。
- 降级：非核心功能关闭或兜底，保核心链路。
- 限流：控制请求速率，令牌桶/漏桶/滑动窗口（网关/单机，Guava RateLimiter/Sentinel）。

=== 5. 如何保证接口幂等？

- 定义：同一请求重复执行结果一致。
- 方案：数据库唯一索引、Redis `setnx`、状态机（非法转移拒绝）、token 防重复提交、乐观锁（version）。

=== 6. 如何设计一个秒杀系统？

- 前端：静态化 + CDN、按钮防抖。
- 网关：限流、风控、校验。
- 后端：Redis 预减库存（Lua 原子）+ MQ 异步下单 + DB 最终扣减。
- 防超卖：Redis `decr`/Lua 判断 + DB 乐观锁兜底。
- 削峰：消息队列缓冲；防刷：验证码、风控、单用户限购。

=== 7. 如何设计一个短链接系统？

- 发号：自增 ID/雪花 → Base62 编码；或哈希 + 冲突处理。
- 存储：Redis 热数据 + DB 持久。
- 重定向：301（永久省请求）/302（便于统计）。
- 优化：布隆过滤器防无效查询、缓存热点。

=== 8. 分布式锁有哪些实现？优缺点？

- Redis：`SET NX EX` + Lua 释放 + 看门狗，性能高但主从切换可能丢锁。
- ZooKeeper：临时顺序节点，强一致但写性能低。
- etcd：租约 + 事务，强一致。
- 要点：互斥、防误删（唯一 token）、可重入、自动续期。

=== 9. 注册中心 CAP 取舍（ZooKeeper vs Eureka vs Nacos）？

- ZooKeeper：CP，强一致，网络分区时可能拒绝服务。
- Eureka：AP，可用性优先，各节点可读旧数据，自我保护。
- Nacos：AP + CP 可切换（默认 AP，临时实例 AP / 持久实例 CP）。
- 服务发现更看重可用性，故常用 AP 型。

=== 10. 如何设计一个高并发、高可用的系统？

- 高并发：水平扩展（无状态 + 负载均衡）、多级缓存、异步（MQ）、池化、读写分离、分库分表、CDN。
- 高可用：冗余副本、故障转移、资源隔离、容灾多活、监控告警、灰度发布。

=== 11. 什么是 Service Mesh？解决什么问题？

- Service Mesh（如 Istio/Envoy）：以 sidecar 代理下沉服务治理（流量管理、熔断、限流、安全、可观测性），业务代码与基础设施解耦。
- 解决：多语言统一治理、治理逻辑与业务解耦、减少 SDK 升级负担。

=== 12. 链路追踪如何实现？

- 一次请求生成全局 `traceId`，跨服务透传（HTTP Header/RPC 元数据），每个服务生成 `span` 记录耗时与父子关系，上报到 SkyWalking/Zipkin/Jaeger，据此还原调用链与定位慢节点。

=== 13. 分布式 ID 生成方案有哪些？

- UUID（无序，索引差）、数据库号段（批量分配）、Redis 自增（依赖 Redis）、雪花算法（趋势递增，需处理时钟回拨）。
- 雪花：时间戳 + 机器 ID + 序列号。

=== 14. 你的项目如何做技术选型与权衡？

- 答题框架：需求（QPS/数据量/一致性）→ 候选方案对比（性能/成本/维护/团队熟悉度）→ 选择与理由 → 权衡与取舍（强一致 vs 最终一致、同步 vs 异步）。
- 结合自己项目：如选 MySQL 而非 TiDB 因团队熟悉与成本；选 Kafka 而非 RocketMQ 因大数据场景等。
