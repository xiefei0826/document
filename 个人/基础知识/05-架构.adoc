架构篇聚焦分布式理论、微服务治理、高并发/高可用设计、常见系统设计方案与权衡。

== 分布式理论

=== CAP

- 一致性（Consistency）、可用性（Availability）、分区容错（Partition tolerance），三者不可兼得，P 必选。
- 实践：CP（ZooKeeper/etcd，强一致牺牲可用）、AP（Eureka，高可用牺牲强一致）。
- 主流是 BASE（Basically Available 基本可用、Soft state 软状态、Eventually consistent 最终一致）。

=== 一致性模型与协议

- 强一致、弱一致、最终一致。
- 2PC（两阶段提交）：同步阻塞、单点、数据不一致风险。
- 3PC：引入超时与预提交，缓解阻塞。
- TCC（Try-Confirm-Cancel）：业务层补偿，`Try` 预留、`Confirm` 确认、`Cancel` 回滚。
- 本地消息表 / 事务消息（RocketMQ 半消息）：最终一致。
- Saga：长事务拆多本地事务 + 补偿。
- Paxos / Raft：分布式共识（多数派），选主与日志复制。

=== 分布式事务选型

- 单库：本地事务。
- 跨库跨服务强一致场景少，多采用最终一致：TCC、Saga、事务消息 + 本地消息表。
- 原则：能用幂等 + 重试 + 补偿解决就不用强一致。
- 具体组件与落地方式见下节「分布式事务：常用组件与实现方式」。

== 分布式事务：常用组件与实现方式

分布式事务没有银弹：强一致（XA/2PC）以资源锁定和可用性为代价，工程上更常用的是「补偿 + 可靠消息」的最终一致。下面按 *实现方式 → 具体组件 → 落地注意点* 梳理。

=== 实现方式与组件总览

[cols="2,1,1,1,3,3"]
|===
| 实现方式 | 一致性 | 侵入性 | 性能 | 代表组件 | 适用场景
| XA / 2PC | 强一致 | 低 | 低 | Seata XA / Atomikos / Narayana / ShardingSphere | 短事务、同机房跨库、必须强一致
| AT | 最终一致 | 极低 | 中 | Seata AT | Java + 关系库、想零改造接入
| TCC | 最终一致 | 高 | 高 | Seata TCC / DTM / ByteTCC | 金融支付、需要资源预留
| Saga | 最终一致 | 中 | 高 | Seata Saga / Camunda / Temporal / DTM | 长事务、跨外部系统
| 本地消息表 | 最终一致 | 中 | 高 | 自研定时任务 / Canal | 异步解耦、MQ 无事务能力
| 事务消息 | 最终一致 | 低 | 高 | RocketMQ（半消息） | 异步削峰、上下游解耦
| 最大努力通知 | 最终一致 | 低 | 高 | 定时重试 + 对账 | 对外回调、允许延迟
|===

=== 常见实现方式详解

==== 2PC / XA（资源层强一致）

- 流程：协调者发起 Prepare，各参与者预提交并持锁 → 全部成功则 Commit，任一失败则 Rollback。
- 优点：强一致，业务几乎无侵入（依赖数据库 XA 接口）。
- 缺点：同步阻塞、协调者单点、资源锁定时间长、网络分区可能悬挂，跨服务长事务不适用。
- 落地：JTA 实现（Atomikos / Narayana / Bitronix）、ShardingSphere XA、Seata XA；MySQL 需 5.7+ 才有较完善的 XA 支持。

==== TCC（业务层补偿）

- 三阶段：`Try` 预留资源（冻结金额/库存）→ `Confirm` 真正扣减 → `Cancel` 释放预留。
- 优点：不长期持有数据库锁，性能高，隔离策略可自定义。
- 缺点：每个操作要写三个方法，业务侵入大；必须处理空回滚、幂等、悬挂。
- 落地：Seata TCC（`@TwoPhaseBusinessAction`）、DTM、ByteTCC、TCC-Transaction。

==== Saga（长事务 + 补偿编排）

- 把长事务拆成一串本地事务 T1…Tn，每个配一个补偿 C1…Cn；某步失败则从当前点逆向执行补偿。
- 两种编排：*协同式 Choreography*（事件驱动、无中心协调者，链路复杂后难维护）、*编排式 Orchestration*（中心协调器/状态机，可观测性好，更推荐）。
- 优点：不阻塞、适合跨外部系统与长流程。
- 缺点：一阶段就已提交，缺乏隔离性（可能脏读）；补偿逻辑复杂且不保证一定成功。
- 落地：Seata Saga（JSON 状态机）、Camunda / Flowable / Zeebe、Temporal / Cadence、Axon / Eventuate Tram、DTM。

==== 本地消息表

- 业务库建消息表，*业务数据与消息记录在同一个本地事务*写入 → 后台任务轮询发送 MQ → 成功后标记已发送 → 消费端幂等。
- 可用 Canal 监听 binlog 替代轮询，降低侵入与延迟。
- 优点：不依赖 MQ 的事务能力，可靠性高，任何数据库都能用。
- 缺点：消息表与业务库耦合、有轮询延迟、需处理重复发送。

[source,sql]
----
CREATE TABLE t_local_message (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  biz_no        VARCHAR(64) NOT NULL COMMENT '业务单号',
  payload       TEXT        NOT NULL COMMENT '消息内容',
  topic         VARCHAR(64) NOT NULL,
  status        TINYINT     NOT NULL DEFAULT 0 COMMENT '0待发 1已发 2失败',
  retry_count   INT         NOT NULL DEFAULT 0,
  next_retry_at DATETIME    NOT NULL,
  created_at    DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_status_retry (status, next_retry_at)
) ENGINE=InnoDB;
----

==== 事务消息（半消息）

- RocketMQ：发半消息（对消费者不可见）→ 执行本地事务 → 回执 commit/rollback → 未回执时 Broker 定时 *回查* 本地事务状态 → 确定投递或丢弃。
- 优点：无需自建消息表，与业务解耦，吞吐高。
- 缺点：强依赖 MQ；回查接口必须能查到确定的事务结果；消费端仍需幂等。

==== 最大努力通知 + 对账兜底

- 通知方按退避策略重试（如 1min / 5min / 30min / 2h…），达上限后进死信并告警；接收方提供幂等的查询/回执接口。
- 配合定时对账任务（T+1 或准实时）扫描状态异常单，主动补偿或转人工。
- 这是 *所有方案的最后一道防线*：任何分布式事务都要有对账与人工兜底。

=== 常用组件

==== Seata（Java 生态最主流）

三个角色：

- *TC*（Transaction Coordinator）：独立部署的 `seata-server`，维护全局事务与分支事务状态，驱动全局提交/回滚。
- *TM*（Transaction Manager）：嵌在业务应用，用 `@GlobalTransactional` 标记全局事务边界，向 TC 发起开启/提交/回滚。
- *RM*（Resource Manager）：嵌在业务应用，管理分支事务，向 TC 注册分支、上报状态、执行本地提交/回滚。
- 全局事务 ID（*XID*）沿 RPC 调用链透传，Seata 已适配 Dubbo / Feign / gRPC 等。

四种模式：

[cols="1,3,2,2"]
|===
| 模式 | 原理 | 优点 | 限制
| AT（默认） | 拦截 SQL 生成前后镜像写入 `undo_log`，与业务 SQL 在同一本地事务提交；二阶段异步删 undo，或按 before image 生成反向 SQL 补偿；TC 持 *全局锁* 防脏写 | 零业务侵入，一个注解即可接入 | 仅支持关系库、需建 `undo_log` 表、全局锁有开销
| TCC | 业务实现 Try/Confirm/Cancel，Seata 负责调度与容错 | 不长期持锁、性能高 | 三方法开发量大，需处理空回滚/幂等/悬挂
| Saga | 状态机编排正向服务与补偿服务，一阶段直接提交 | 适合长事务、跨外部系统 | 无隔离性，补偿需业务保证
| XA | 基于数据库原生 XA 的 2PC | 强一致、标准协议 | 资源锁定久，需 DB 支持 XA
|===

- TC 必须高可用部署（多节点 + 全局事务状态持久化到 DB/Redis），否则成为单点。

==== JTA / XA 与分库分表组件

- *Atomikos / Narayana / Bitronix*：Java 应用内嵌的 JTA 事务管理器实现。
- *ShardingSphere*：分库分表场景整合 XA（Atomikos/Narayana）或 BASE 柔性事务（Seata AT）。
- MySQL XA 语句：`XA START / END / PREPARE / COMMIT / ROLLBACK`。

==== Saga / 工作流编排类

- *Seata Saga*、*ServiceComb Saga*（华为）：状态机式补偿编排。
- *Camunda / Flowable / Zeebe*：BPMN 工作流引擎，用流程节点 + 补偿节点实现长事务。
- *Temporal / Cadence*：持久化工作流，「代码即工作流」，自带重试、超时、补偿，长事务场景越来越常用。
- *Axon Framework / Eventuate Tram*：事件溯源 + Saga，配合 CDC（binlog / WAL）做可靠消息。

==== 消息、对账与跨语言组件

- *RocketMQ*：事务消息（半消息 + 回查）。
- *Kafka*：`enable.idempotence` + 事务 API + `read_committed`，保证流处理内的 exactly-once；跨服务业务事务仍需业务幂等。
- *RabbitMQ*：publisher confirm + 手动 ack，本身无半消息能力，通常配合本地消息表。
- *Canal*：伪装成 MySQL slave 订阅 binlog，用于异步投递、缓存删除、对账。
- *DTM*（Go，跨语言）：一个框架同时支持 TCC、Saga、XA、二阶段消息、Workflow，非 Java 栈常选。
- *Tx-LCN / LCN 模式*：国内早期框架，已停止维护，仅作了解，不推荐新项目使用。
- *分布式数据库自带*：TiDB（Percolator + TSO 的 2PC）、OceanBase、CockroachDB 在数据库层解决跨节点事务，应用侧无需额外框架。

=== 选型速查

. 单库单服务 → 本地事务，不要引入分布式事务。
. 跨库、同一应用、同机房、必须强一致 → XA（Seata XA / ShardingSphere XA）。
. Java 微服务、以关系库为主、想快速接入 → Seata AT。
. 金融/资金/库存，需要资源预留且性能要求高 → TCC（Seata TCC / DTM）。
. 长流程、跨外部系统（第三方支付、物流） → Saga（Seata Saga / Temporal / Camunda）。
. 异步解耦、允许秒级延迟 → RocketMQ 事务消息 或 本地消息表。
. 对外通知、允许更长时间不一致 → 最大努力通知 + 对账兜底。
. 非 Java / 多语言栈 → DTM，或 MQ + 幂等自研。
. 无论哪种 → 幂等、重试、监控告警、对账兜底都必须有。

=== 落地注意点（面试高频）

- *幂等是前提*：Confirm/Cancel、消息消费、事务回查、补偿、重试全部要幂等（唯一索引、状态机、去重表）。
- *TCC 三大坑*：空回滚（Try 未执行却收到 Cancel）、幂等、悬挂（Cancel 比 Try 先到）→ 用分支事务状态表 + 唯一索引判定与拦截。
- *隔离性*：AT 靠 TC 全局锁防脏写；TCC/Saga 一阶段已提交、无隔离，需用「冻结金额 / 中间状态」等业务设计避免脏读。
- *补偿不保证成功*：必须有重试退避、死信告警、人工处理入口，以及 T+1 对账兜底。
- *事务边界尽量小*：长事务锁资源、易超时、回滚链长、可用性差。
- *XID 透传*：跨服务调用链必须传递全局事务 ID，否则分支事务无法关联到全局事务。
- *协调者高可用*：Seata Server 多节点 + 状态持久化（DB/Redis），避免单点。
- *回查接口要可靠*：事务消息的回查必须能返回确定的本地事务结果，否则消息长期悬挂。
- *可观测性*：监控全局事务成功率、悬挂/回滚失败数、补偿失败队列、消息积压。
- *能不用就不用*：优先「本地事务 + 可靠消息 + 幂等」，强一致只放在真正必要的环节。

== 分布式 ID

- UUID：无序，索引性能差。
- 数据库号段：批量分配段。
- Redis 自增：简单但依赖 Redis。
- 雪花算法：时间戳 + 机器 ID + 序列号，趋势递增，需处理时钟回拨（拒绝/等待/备用机器位）。

== 分布式锁

- 实现：Redis（`SET NX EX` + Lua 释放 + Redisson 看门狗）、ZooKeeper（临时顺序节点）、etcd（租约 + 事务）。
- 要点：互斥、防误删（唯一 token）、可重入、自动续期、可重试。

== 微服务

=== 拆分原则

- 单一职责、高内聚低耦合、按业务域（DDD 限界上下文）。
- 服务粒度：过细导致分布式复杂度，过粗难维护。

=== 服务治理

- *注册中心*：服务注册与发现（Nacos/Eureka/Consul/etcd）。
- *配置中心*：动态配置（Nacos/Apollo）。
- *网关*：统一入口、鉴权、路由、限流、日志（Spring Cloud Gateway/Kong/Nginx）。
- *负载均衡*：客户端负载（Ribbon/LoadBalancer）、服务端负载（Nginx/LVS）。
- *服务调用*：RPC（Dubbo/gRPC）与 REST（OpenFeign）。

=== 熔断、限流、降级

- 熔断：调用失败率超阈值打开熔断器，快速失败（Sentinel/Resilience4j/Hystrix）。
- 限流：令牌桶、漏桶、滑动窗口；网关/单机限流。
- 降级：非核心功能关闭或走兜底，保核心链路。

=== 链路追踪与可观测性

- 指标（Metrics）：Prometheus + Grafana。
- 日志（Logging）：集中式 ELK/Loki。
- 链路（Tracing）：SkyWalking/Zipkin/Jaeger，分布式 traceId 贯穿。

=== 服务网格

- Service Mesh（Istio/Envoy）：将治理下沉到 sidecar 代理，解耦业务与基础设施。

== 熔断与限流：常用组件及优缺点

先分清三件事：*熔断* 是下游不稳时快速失败、防雪崩，作用在「调用方」；*限流* 是控制请求速率保护自己，作用在「被调方 / 入口」；*降级* 是熔断或限流触发后的业务兜底动作。

组件按 *三个层次* 分：*SDK 层*（Resilience4j / Sentinel，粒度细、有侵入）、*网关层*（Nginx / Gateway / APISIX，统一入口、粗粒度）、*Mesh 层*（Istio，语言无关、零侵入但运维重）。生产通常是组合拳：网关挡总量 → SDK 做资源级熔断与细粒度限流 → 系统自适应保护兜底。

TIP: 算法决定「突发流量怎么处理」，组件决定「在哪一层生效、是否集群统一、能否动态配置、有没有控制台」。选型先定层次，再定算法。

=== 熔断与容错组件

[cols="2,2,3,3"]
|===
| 组件 | 定位 | 优点 | 缺点
| Hystrix | Netflix，已停维 | 成熟的熔断器实现、线程/信号量隔离（舱壁模式）、fallback、请求缓存与合并、Dashboard；Spring Cloud Netflix 集成好、资料多 | *2018 起停止维护*；线程池隔离开销大（每个依赖一个线程池）；配置繁琐；与 Spring Boot 3 及新生态不兼容；新项目不要选
| Resilience4j | Hystrix 官方推荐的替代，轻量库 | 只依赖 Vavr、无重依赖；函数式装饰器风格；模块按需引入（CircuitBreaker / RateLimiter / Retry / Bulkhead / TimeLimiter）；滑动窗口统计、开销小；支持 `CompletableFuture` 与 Reactor；与 Spring Boot 3、Micrometer 集成好；社区活跃 | *无控制台、无集中规则下发*，多实例规则各自配置；功能少于 Sentinel（无系统自适应保护、热点参数限流、集群流控）；监控需自行接 Prometheus/Grafana；主要面向 Java
| Sentinel | 阿里，国内主流，一站式 | 功能最全：流控、熔断降级、热点参数限流、系统自适应保护、黑白名单、网关流控、集群流控；*Dashboard 可视化 + 规则动态下发*（可接 Nacos/Apollo/ZK 持久化）；资源维度细；与 Spring Cloud Alibaba / Dubbo 深度集成；中文资料丰富 | 控制台需单独部署，*默认规则存内存、重启丢失*，必须接数据源；集群流控要部署 Token Server，复杂度上升；侵入性略高（`@SentinelResource` 或埋点）；以 Java 生态为主；Spring Boot 3 需对应版本
| Spring Cloud Circuit Breaker | 抽象层（非具体实现） | 统一 API，底层可切换 Resilience4j / Sentinel；与 Spring 生态一致，迁移成本低 | 只是抽象，能力受底层实现限制；高级特性仍需直接调用底层 API
| Istio / Envoy | Service Mesh 层 | 语言无关、业务零侵入；熔断（outlier detection、连接池熔断）、限流、重试、超时统一由控制面下发；适合多语言异构系统 | 引入控制面 + sidecar，运维与资源成本高；每请求多一跳带来延迟；粒度较粗、不如 SDK 灵活；全局限流需额外部署 ratelimit 服务与 Redis
|===

- *Hystrix 为什么退出*：线程池隔离虽彻底，但每依赖一个线程池带来线程与上下文切换开销，且项目已停止维护；Resilience4j 用无隔离/信号量 + 轻量函数式设计取而代之。
- *Resilience4j vs Sentinel 怎么选*：只要轻量容错、不需要控制台 → Resilience4j；要 Dashboard、动态规则、热点参数与系统保护（国内 Alibaba 生态）→ Sentinel。

=== 限流组件（按实现层次）

[cols="2,3,3,3"]
|===
| 组件 | 实现 / 算法 | 优点 | 缺点
| Guava RateLimiter | 单机 / 令牌桶（SmoothBursty、SmoothWarmingUp） | 极轻量、零外部依赖、API 简单、支持预热 | *仅单机 JVM*，集群需按实例数均分配额；速率不能动态调整（需重建）；无监控、无控制台、无持久化规则
| Bucket4j | 单机 / 令牌桶，可经 Hazelcast、Redis、Infinispan、JCache 扩展为分布式 | 功能丰富（多带宽、精确并发控制、配置可动态修改）、支持分布式扩展 | 仅 Java；分布式需额外依赖；无控制台；配置仍偏代码化
| Redis + Lua | 分布式 / 计数器、滑动窗口（ZSet）、令牌桶（Hash + Lua） | 集群统一计数、Lua 保证原子、实现可控、不引入新中间件 | 每请求一次 Redis 往返（增加延迟，Redis 成为热点与单点）；精确滑动窗口在高 QPS 下内存与清理成本高；Redis 故障要有降级策略；依赖时钟
| Spring Cloud Gateway `RequestRateLimiter` | 网关 / 令牌桶（Redis + Lua） | 与路由体系集成、可按路由/用户/IP 维度限流、在入口挡流量 | 强依赖 Redis；规则动态性一般；只能做网关层粗粒度控制
| Nginx `limit_req` / `limit_conn` | 网关 / 漏桶、连接数限制 | 性能极高、在最外层挡量、语言无关、稳定成熟 | 配置静态、改规则需 reload；策略简单、无熔断能力；无动态配额与集中管控
| Kong / APISIX | 网关 / 插件化（固定窗口、滑动窗口、令牌桶，可接 Redis 集群计数） | 插件丰富、规则动态生效、支持集群限流、有管理 API | 引入额外组件与运维成本；高 QPS 下插件与 Redis 都有开销
| Sentinel 集群流控 | SDK + Token Server / 滑动窗口 | 精确控制 *集群总配额*，与熔断、系统保护一体，Dashboard 配置 | 需部署 Token Server 并保障其高可用；Java 生态为主
| Istio / Envoy 全局限流 | Mesh / 本地限流 + 全局 ratelimit | 语言无关、集中配置、业务零侵入 | 需额外 ratelimit 服务与 Redis；延迟与复杂度增加；粒度较粗
| 自适应限流 | 系统保护（Sentinel 系统规则、Netflix concurrency-limits、Envoy overload manager） | 无需人工设固定阈值，按 CPU、Load、平均 RT、并发数动态调节，适配容量变化 | 算法复杂、调参难、可能误判；强依赖可观测性
|===

=== 选型建议

. 新项目 Spring Boot 2/3、不需要控制台、只要熔断与重试 → *Resilience4j*。
. 国内 Spring Cloud Alibaba / Dubbo、要 Dashboard 与动态规则、要热点参数和系统保护 → *Sentinel*。
. 存量 Hystrix → 迁移到 Resilience4j 或 Sentinel，不要再新增依赖。
. 只想给单个方法/接口限个速 → *Guava RateLimiter*（务必记住是单机维度）。
. 集群精确配额 → *Redis + Lua*（简单可控）或 *Sentinel 集群流控*（有控制台）。
. 统一入口挡总量 → *Nginx*（最外层最省）或 *Gateway / APISIX*（需要动态规则与配额维度）。
. 多语言异构、追求业务零侵入 → *Istio*，但要先评估运维与延迟成本。
. *组合拳*：Nginx 挡总量 → 网关按租户/接口配额 → SDK 做资源级熔断与热点参数限流 → 系统自适应保护兜底。

=== 落地注意点（熔断限流）

- *阈值从哪来*：由压测得出单机容量再按实例数换算，不要拍脑袋；硬编码固定值在弹性扩缩容下会失准。
- *单机 vs 集群*：单机限流在实例数变化时总配额会漂移；集群限流要评估 Redis 往返延迟与可用性。
- *被限流后的行为*：返回 `429`、友好提示、排队或降级兜底，别直接抛 500；被拒请求要有可观测指标。
- *熔断状态机*：Closed → Open → *Half-Open*，半开状态只放少量探测流量，成功才恢复，避免反复震荡。
- *隔离策略*：线程池隔离（Hystrix，彻底但开销大）vs 信号量隔离（Sentinel/Resilience4j，轻量但不隔离慢调用占用的线程）；舱壁隔离防止一个慢依赖吃光所有线程。
- *降级兜底*：fallback 必须轻量、无远程依赖、可返回缓存或默认值；fallback 自身也可能被打垮。
- *规则动态化与持久化*：Sentinel 默认规则存内存，需接 Nacos/Apollo；配置中心故障时要能用本地快照。
- *避免误熔断*：统计窗口太短易被瞬时抖动触发；要设 *最小请求数* 与慢调用比例阈值，区分「异常比例」与「慢调用比例」。
- *重试与熔断配合*：重试会放大流量，熔断打开时应停止重试；重试要加退避与抖动，避免惊群。
- *可观测性*：熔断状态变更、限流拒绝数、RT 分位数、下游成功率都要有监控告警。
- *别把限流当解决方案*：它只是保护手段，根因往往是容量不足或代码问题，需配合扩容、缓存、异步化。

== 高并发与高可用

=== 高并发

- 水平扩展：无状态服务 + 负载均衡。
- 缓存：本地缓存（Caffeine）+ 分布式缓存（Redis）多级。
- 异步：MQ 削峰、异步化。
- 池化：连接池、线程池。
- 读写分离、分库分表、CDN、静态化。

=== 高可用

- 冗余：多副本、主备、集群。
- 故障转移：健康检查、自动切换。
- 隔离：资源隔离（线程池/信号量）、舱壁隔离。
- 容灾：多机房、异地多活。
- 监控告警 + 应急演练。

=== 幂等

- 定义：同一请求重复执行结果一致。
- 方案：唯一索引（insert）、Redis `setnx`、状态机（非法状态转移拒绝）、token（防重复提交）、悲观锁/乐观锁。

== 常见系统设计

=== 秒杀系统

- 前端：静态化 + CDN、按钮防抖。
- 网关：限流、校验。
- 后端：Redis 预减库存（Lua 原子）+ MQ 异步下单 + 数据库最终扣减。
- 防超卖：Redis `decr` 原子 / Lua 判断；DB 乐观锁兜底。
- 削峰：消息队列缓冲，下单与扣减解耦。
- 防刷：验证码、风控、单用户限购。

=== 短链接系统

- 发号：自增 ID / 雪花 → Base62 编码；或哈希 + 冲突处理。
- 存储：KV（Redis 热数据 + DB 持久）。
- 重定向：301（永久，省请求）/ 302（临时，便于统计）。
- 优化：布隆过滤器防无效查询、缓存热点。

=== 排行榜

- Redis ZSet：`ZADD/ZINCRBY/ZREVRANGE`，支持实时更新与 TopN。
- 大用户量：分片 + 聚合、定时离线计算。

=== 消息推送 / 未读数

- 全量 vs 增量推送、分桶、Redis 计数 + 懒加载、离线消息存储。

=== 限流算法实现

- 固定窗口：简单，边界突刺。
- 滑动窗口：更平滑。
- 漏桶：恒定速率，应对突发差。
- 令牌桶：允许一定突发，`Guava RateLimiter`、Redis + Lua。

== 字段级权限设计（列级数据权限）

典型场景：*销售不能看进货价*、客服只能看手机号后四位、普通员工看不到同事薪资、导出报表按角色脱敏。这类需求也叫 *列级权限 / 字段级数据权限 / 动态脱敏*。

先把它放进权限体系里定位，三层是叠加关系：

- *功能权限*：能不能访问这个菜单/接口。
- *行级权限*：能不能看到这一行（如只看本部门订单）。
- *字段级权限*：这一行里 *哪些列* 能看、能改 ← 本节主题。

执行顺序一般是：功能权限 → 行级过滤 → 字段裁剪/脱敏。

=== 权限模型与配置设计

- 用 *RBAC* 表达「角色 → 字段」，用 *ABAC* 补条件（部门、岗位、数据归属、金额区间、环境），组合起来最灵活。
- 配置维度六要素：*资源*（哪个实体/接口/报表）、*字段*（哪个列，可支持字段组与通配）、*主体*（角色/用户/部门/岗位/租户）、*条件*（ABAC 表达式）、*效果*（可见 / 隐藏 / 脱敏 / 只读 / 可写）、*优先级*。
- *默认策略必须是「拒绝」*：敏感字段登记后默认不可见，只有显式授权才放行（最小权限）；反过来「默认全可见、逐个配黑名单」一定会有漏配。
- *冲突合并*：用户多角色时，敏感字段按 *DENY 优先 / 最严格优先*，显式拒绝高于允许。

配置表示例（规则表 + 字段元数据表）：

[source,sql]
----
CREATE TABLE t_sensitive_field (
  field_code     VARCHAR(64) PRIMARY KEY COMMENT '字段码，如 goods.purchase_price',
  table_name     VARCHAR(64) NOT NULL,
  column_name    VARCHAR(64) NOT NULL,
  default_effect VARCHAR(16) NOT NULL DEFAULT 'DENY' COMMENT '默认拒绝',
  mask_type      VARCHAR(16) NOT NULL DEFAULT 'HIDE' COMMENT 'HIDE/NULL/PARTIAL/CONST/HASH',
  data_level     VARCHAR(16) NOT NULL COMMENT '敏感等级 L1~L4',
  created_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE t_field_permission (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  resource_code  VARCHAR(64) NOT NULL COMMENT '资源码，如 goods:detail / goods:export',
  field_code     VARCHAR(64) NOT NULL COMMENT '关联 t_sensitive_field',
  subject_type   VARCHAR(16) NOT NULL COMMENT 'ROLE/USER/DEPT/POST/TENANT',
  subject_id     VARCHAR(64) NOT NULL,
  effect         VARCHAR(16) NOT NULL COMMENT 'ALLOW/DENY/MASK/READONLY/WRITABLE',
  mask_type      VARCHAR(16) NULL,
  condition_expr VARCHAR(256) NULL COMMENT 'ABAC 条件，如 dept == owner_dept',
  priority       INT NOT NULL DEFAULT 0,
  enabled        TINYINT NOT NULL DEFAULT 1,
  created_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_rule (resource_code, field_code, subject_type, subject_id)
) ENGINE=InnoDB;
----

「销售不能看进货价」的配置：

[cols="2,2,2,3"]
|===
| 主体 | effect | mask_type | 结果
| `role:sales` | `DENY` | `HIDE` | 返回体中直接移除 `purchasePrice`
| `role:sales_manager` | `MASK` | `PARTIAL` | 只显示价格区间或打码
| `role:purchase` | `ALLOW` | - | 完整可见
| `role:finance` | `ALLOW` | - | 完整可见
| 其它未配置 | `DENY`（默认） | `HIDE` | 最小权限兜底
|===

配置存放与生效：规则放 *配置中心*（Nacos / Apollo）或 DB，应用启动时加载 + 本地缓存（Caffeine），变更通过监听刷新；*不要每次请求查库*。角色变动时要主动失效用户维度的权限计算结果缓存。

=== 实现方案对比：在哪一层做

[cols="2,3,3,4"]
|===
| 层次 | 做法 | 优点 | 缺点
| 前端 | 隐藏表格列、不渲染 | 实现简单、体验好 | *完全不安全*：接口已返回数据，抓包或改前端即可拿到；只能作为展示配合
| 应用层·序列化出口 | Jackson `@JsonView`、自定义 Serializer、`ResponseBodyAdvice` 统一过滤 | 侵入小、按接口灵活、可统一收口所有出参 | 敏感数据已被查进内存；导出、日志、消息容易漏；需框架强制约束
| 应用层·VO 分层 | 按角色返回不同 VO / DTO | 类型安全、清晰 | 角色 × 接口组合爆炸，维护成本高
| ORM 层·动态列 | MyBatis `<if>` 控制 `SELECT` 列、JPA Projection | *SQL 层就不取敏感列*，内存里也没有，实现可靠 | 要为每个查询显式写列；禁止 `SELECT *`；动态 SQL 文本变多
| ORM 层·拦截器 | MyBatis Interceptor 改写 SQL 列、TypeHandler 脱敏 | 统一收口、业务无感 | 改写复杂 SQL（别名、join、子查询、函数）风险高；影响 SQL 缓存与执行计划
| 数据库视图 | 按角色建 `view_sales_goods`（不含 `purchase_price`） | DB 层强约束、性能好、应用无感 | 视图随角色膨胀；分库分表/跨库难；DDL 管理重
| 数据库列级授权 | `GRANT SELECT(col1, col2) ON t TO role` | 约束最强 | 应用通常用 *统一连接池账号*，DB 用户 ≠ 业务用户，实际基本不可行
| 数据库动态脱敏 | Oracle Data Redaction、SQL Server DDM、部分云数据库 | 对应用透明、漏改风险低 | 依赖特定/商业数据库；策略表达力有限；MySQL 社区版无原生能力
| SQL 网关 / 代理 | ShardingSphere 脱敏、自研 SQL 解析改写 | 跨语言统一 | 架构复杂，SQL 解析兼容性风险
|===

=== 推荐落地组合

. *登记元数据*：把敏感字段（含等级、默认策略、脱敏方式）集中登记，作为唯一事实源。
. *配置规则*：配置中心维护「主体 × 资源 × 字段 → 效果」，本地缓存 + 变更监听。
. *双保险执行*：
   - *SQL 层做列裁剪*（动态列或视图），敏感数据根本不进内存；
   - *序列化出口再做一次过滤/脱敏*（`ResponseBodyAdvice` 统一收口），兜住缓存对象、RPC 返回、第三方数据等来源。
. *全链路一致*：列表、详情、导出、报表、打印、日志、消息推送、开放 API、搜索引擎索引、数据同步都走同一套「可见字段集合」。
. *审计与测试*：记录谁在何时访问了哪个敏感字段；把字段权限纳入自动化用例，防止新增接口漏配。

=== 端到端示例：销售不能看进货价

*1）标注字段*

[source,java]
----
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface FieldAuth {
    String code();
    MaskType mask() default MaskType.HIDE;
}

public class GoodsVO {
    private Long id;
    private String name;
    private BigDecimal salePrice;

    @FieldAuth(code = "goods.purchase_price")
    private BigDecimal purchasePrice;
}
----

*2）SQL 层裁剪列*（MyBatis 动态列，比运行时改写 SQL 更稳妥）

[source,xml]
----
<select id="getGoods" resultType="GoodsVO">
    SELECT id, name, sale_price
    <if test="perm.canSeePurchasePrice">, purchase_price</if>
    FROM t_goods WHERE id = #{id}
</select>
----

*3）出口统一过滤*（`ResponseBodyAdvice` 示意，按注解与可见字段集合裁剪）

[source,java]
----
Set<String> visible = permission.visibleFields("goods:detail", currentUser());
Map<String, Object> body = toMap(result);
for (FieldMeta meta : authFields(result.getClass())) {
    if (!visible.contains(meta.code())) {
        body.remove(meta.fieldName());          // HIDE
        // 或 body.put(meta.fieldName(), mask(value, meta.maskType()));  // MASK/NULL/CONST
    }
}
return body;
----

*4）写权限同样要收口*：不能把请求体直接透传给 `update`；按「可写字段白名单」拷贝，否则销售虽看不到进货价，却可能通过更新接口改掉它。

[source,java]
----
// 反例：BeanUtils.copyProperties(request, entity) —— 会把受限字段一起写入
BeanUtils.copyProperties(request, entity, writableFields(perm)); // 白名单拷贝
----

*5）防推断*：销售被禁止按 `purchase_price` *排序、过滤、范围查询、聚合*（如 `SUM`/`AVG`），否则可用二分或聚合结果反推出真实值。字段权限必须同时约束 `WHERE` / `ORDER BY` / `GROUP BY` / 函数参数，以及搜索、导出、报表条件。

=== 容易忽略的坑（面试高频）

- *前端隐藏不等于权限*：接口返回了就是泄露，必须服务端控制。
- *禁止 `SELECT *`*：新加的敏感列会被悄悄带出来；缓存中的完整对象、RPC 返回值也不能直接透传。
- *越权推断*：字段不返回，但允许按它排序/过滤/聚合/模糊搜索，仍能推出值；ES 索引里同步了敏感字段也会泄露。
- *出口不止 HTTP*：Excel 导出、报表、打印、日志（`log.info("{}", vo)`）、MQ 消息、开放平台 API、数据同步、BI 数据集都要过同一套规则。
- *读权限 ≠ 写权限*：还要控制新增/修改/批量导入/Excel 模板是否包含该列。
- *多角色叠加*：显式 `DENY` 优先；别用「有任一角色允许就放行」。
- *分页与聚合口径*：先做列裁剪再统计，可能导致平均值/总额按错误口径计算；明确「按可见数据算」还是「按全量算但只展示脱敏结果」。
- *缓存与性能*：规则要缓存；动态列会让 SQL 文本变多、降低执行计划缓存命中率，可按有限几种「权限组合」枚举 SQL。
- *配置变更生效*：配置中心推送 + 本地缓存失效，用户角色调整后要立刻生效，避免权限残留。
- *审计与回归*：敏感字段访问留痕；新增接口、新增字段要有自动化用例校验，最怕「新加的报表漏配」。

=== 面试答题框架

*分层定位（功能/行/字段）→ 元数据登记 + 默认拒绝 → 配置建模（主体×资源×字段×条件×效果）→ 选实现层次（SQL 列裁剪 + 出口脱敏双保险）→ 全链路一致（导出/日志/报表/搜索）→ 防越权推断 → 审计与自动化回归*。

== 设计原则与权衡

- 三高（高性能/高可用/高扩展）与成本权衡。
- 一致性 vs 可用性 vs 分区容错。
- 同步 vs 异步、强一致 vs 最终一致。
- 避免过度设计：先满足当前，预留扩展点。
- 稳定优先：缓存、降级、隔离、监控是基本功。

== SDD 规格驱动开发（AI 辅助研发方法论）

=== 什么是 SDD

SDD（Spec-Driven Development，规格驱动开发）：先产出结构化、可验收的「规格文档」，再由人或 AI 依据规格生成计划、任务与代码，把规格作为整个开发过程的唯一事实源。

- *背景*：早期 AI 编程多是 "vibe coding"（对话式、凭感觉生成），容易出现需求漂移、代码不可控、上下文丢失、反复返工。SDD 把 AI 编码纳入工程化流程：先对齐意图，再执行。
- *与传统开发的区别*：传统需求文档面向人、写完常腐化；SDD 的规格是「机器可读、可执行、可验证」的活文档，AI 直接消费它，并随代码同步演进。
- *为何值得关注*：高级/AI 应用岗面试越来越常问「如何用 AI 工具做工程化开发」「怎么控制 AI 生成代码的质量」。

=== 典型流程

以 GitHub Spec Kit / AWS Kiro 为代表，通常分五个阶段：

. *Specify（规格）*：写清目标、用户故事、范围边界、非功能约束、验收标准 → `spec.md`。
. *Plan（计划）*：技术选型、架构方案、影响范围、风险与备选 → `plan.md`，人工评审。
. *Tasks（任务）*：把计划拆成可独立验证的小任务清单 → `tasks.md`。
. *Implement（实现）*：按任务逐个让 AI 生成代码，小步提交、可回滚。
. *Verify（验证）*：对照验收标准测试与 Review，把偏差回填规格。

- Kiro 对应三段式：Requirements（用 EARS 语法写验收标准）→ Design → Tasks。
- 关键点：每个阶段都要「人审确认」后再进入下一阶段，不让 AI 一路自由发挥。

=== 核心原则

. *规格先行*：先写清楚「做什么、为什么、做到什么算完成」，再写代码。
. *单一事实源*：规格是唯一权威，代码、测试、文档与它对齐；规格变更要版本化。
. *可验收*：需求必须带明确验收标准（输入/输出/边界/异常），模糊需求不进实现。
. *分层拆解*：Epic → Spec → Plan → Tasks 逐层收敛，避免把大需求一次性丢给 AI。
. *小步可验证*：一次一个可验证的增量，完成后立刻编译/测试/Review，再继续。
. *人掌舵、AI 执行*：架构决策、技术选型、取舍由人确认；AI 负责实现与琐碎工作。
. *约束上下文*：用规则文件固定技术栈、代码规范、目录结构、禁区，减少臆造。
. *可追溯*：规格、计划、任务与提交记录关联，变更有据可查，便于回滚。

=== 注意事项与常见坑

- *规格写得太模糊*：AI 只能猜 → 幻觉与返工。必须写清边界、异常、验收条件。
- *规格过于庞大*：上下文爆炸、AI 顾此失彼 → 拆成多个小 spec，按模块/功能分治。
- *只写不更新*：代码改了 spec 没改 → 文档腐化，后续 AI 基于过期规格持续出错。
- *跳过 Plan 直接实现*：AI 容易选错方案，返工代价大。大改动必须先出计划、人工确认。
- *直接信任生成结果*：不编译/不测试/不 Review 就合并；安全、性能、并发、事务需人工把关。
- *上下文污染*：把无关文件、过期规则、大段日志塞进上下文，稀释关键信息；只引用相关文件。
- *规则文件膨胀*：`.cursorrules` / `CODEBUDDY.md` 越写越长反而失效 → 精简、可执行、定期维护。
- *未声明「禁区」*：没明确不许改的范围（线上配置、鉴权、数据库脚本），AI 可能越界。
- *敏感信息入上下文*：密钥、生产数据、个人隐私不要进对话或规则文件。
- *无验收闭环*：任务做完没对照验收标准验证，导致「看起来完成了」。
- *误把回滚当保险*：检查点/回滚只是兜底，不能替代小步提交与代码评审。

=== 工具示例：Cursor

- *规则约束*：`.cursorrules`（旧）或 `.cursor/rules/*.mdc`（新，可按 glob 生效），写技术栈、编码规范、目录约定、禁止事项。
- *Plan 模式*：先让 Agent 输出实施计划而不直接改代码，人工确认后再执行。
- *精确上下文*：`@file`、`@folder`、`@docs` 注入相关文件，避免全库扫描。
- *知识沉淀*：Notepads 保存领域约定、接口契约，作为可复用上下文。
- *实践节奏*：一个 spec 一个会话 → 改动前先 Plan → 改完立刻跑测试 → 再让 AI 自查。

=== 工具示例：CodeBuddy

- *项目规则*：`CODEBUDDY.md` / `.codebuddy/rules/`，声明项目结构、编码规范、构建与测试命令、禁区。
- *模式配合*：Ask（只读问答、先理解代码）→ Plan（出方案、拆任务、人审）→ Craft/Agent（按确认后的方案落地代码）。
- *精确上下文*：`@文件` / `@目录` 指定范围，避免把不相关文件带入。
- *检查点（Checkpoint）*：每阶段可回滚，配合小步提交降低大改风险。
- *实践节奏*：把 spec / plan / tasks 作为文档落到仓库，让 AI 每轮对齐；需求变化先更新文档，再改代码。

=== 落地清单（可直接套用）

. 写 spec：目标、范围、明确不做的事、接口/数据约束、验收标准。
. 出 plan：方案、影响面、风险、备选，人工评审确认。
. 拆 tasks：可独立验证的小任务，标注依赖与验收点。
. 配 rules：技术栈、规范、目录、禁区、构建与测试命令。
. 逐任务实现：Plan → 人工确认 → 生成 → 编译/测试 → Review → 提交。
. 回填规格：需求变化先改 spec，始终保持文档与代码一致。

== 高频真题与参考答案

=== 谈谈你对 CAP 和 BASE 的理解？

- CAP：一致性、可用性、分区容错，三者不可兼得，网络分区（P）必选；分区发生时在 C/A 间取舍，CP 如 ZK/etcd、AP 如 Eureka。
- BASE：基本可用、软状态、最终一致，是 AP 的工程折中，允许短暂不一致、通过异步/补偿最终一致。

=== 分布式事务有哪些方案？如何选型？

- 方案：2PC/3PC（强一致）、TCC（Try-Confirm-Cancel）、Saga（补偿）、本地消息表、事务消息（RocketMQ 半消息）、最大努力通知 + 对账。
- 选型：单库用本地事务；跨库跨服务优先最终一致——可回滚业务用 TCC，长事务用 Saga，消息驱动用事务消息 + 本地消息表；能用幂等+重试+补偿就不用强一致。
- 组件：Seata（AT/TCC/Saga/XA，TC + TM + RM 三角色）、DTM（跨语言）、RocketMQ 事务消息、Atomikos/Narayana（JTA-XA）、ShardingSphere XA、Camunda/Temporal（Saga 编排）；详见「分布式事务：常用组件与实现方式」。

=== 微服务如何拆分？如何治理？

- 拆分：单一职责、高内聚低耦合、按业务域（DDD 限界上下文），粒度适中避免过度拆分。
- 治理：注册中心（Nacos/Eureka）、配置中心（Nacos/Apollo）、网关（Gateway）、负载均衡、熔断限流降级（Sentinel）、链路追踪（SkyWalking）。

=== 熔断、降级、限流的区别与实现？

- 熔断：下游失败率超阈值打开熔断器快速失败，防雪崩（Sentinel/Resilience4j）。
- 降级：非核心功能关闭或兜底，保核心链路。
- 限流：控制请求速率，令牌桶/漏桶/滑动窗口（网关/单机，Guava RateLimiter/Sentinel）。
- 组件取舍：Hystrix 已停维；Resilience4j 轻量但无控制台与集中规则；Sentinel 功能最全、有 Dashboard 但要部署控制台并持久化规则；网关层 Nginx/Gateway/APISIX 挡总量，Mesh 层 Istio 零侵入但运维重。详见「熔断与限流：常用组件及优缺点」。

=== 如何保证接口幂等？

- 定义：同一请求重复执行结果一致。
- 方案：数据库唯一索引、Redis `setnx`、状态机（非法转移拒绝）、token 防重复提交、乐观锁（version）。

=== 如何设计一个秒杀系统？

- 前端：静态化 + CDN、按钮防抖。
- 网关：限流、风控、校验。
- 后端：Redis 预减库存（Lua 原子）+ MQ 异步下单 + DB 最终扣减。
- 防超卖：Redis `decr`/Lua 判断 + DB 乐观锁兜底。
- 削峰：消息队列缓冲；防刷：验证码、风控、单用户限购。

=== 如何设计一个短链接系统？

- 发号：自增 ID/雪花 → Base62 编码；或哈希 + 冲突处理。
- 存储：Redis 热数据 + DB 持久。
- 重定向：301（永久省请求）/302（便于统计）。
- 优化：布隆过滤器防无效查询、缓存热点。

=== 分布式锁有哪些实现？优缺点？

- Redis：`SET NX EX` + Lua 释放 + 看门狗，性能高但主从切换可能丢锁。
- ZooKeeper：临时顺序节点，强一致但写性能低。
- etcd：租约 + 事务，强一致。
- 要点：互斥、防误删（唯一 token）、可重入、自动续期。

=== 注册中心 CAP 取舍（ZooKeeper vs Eureka vs Nacos）？

- ZooKeeper：CP，强一致，网络分区时可能拒绝服务。
- Eureka：AP，可用性优先，各节点可读旧数据，自我保护。
- Nacos：AP + CP 可切换（默认 AP，临时实例 AP / 持久实例 CP）。
- 服务发现更看重可用性，故常用 AP 型。

=== 如何设计一个高并发、高可用的系统？

- 高并发：水平扩展（无状态 + 负载均衡）、多级缓存、异步（MQ）、池化、读写分离、分库分表、CDN。
- 高可用：冗余副本、故障转移、资源隔离、容灾多活、监控告警、灰度发布。

=== 什么是 Service Mesh？解决什么问题？

- Service Mesh（如 Istio/Envoy）：以 sidecar 代理下沉服务治理（流量管理、熔断、限流、安全、可观测性），业务代码与基础设施解耦。
- 解决：多语言统一治理、治理逻辑与业务解耦、减少 SDK 升级负担。

=== 链路追踪如何实现？

- 一次请求生成全局 `traceId`，跨服务透传（HTTP Header/RPC 元数据），每个服务生成 `span` 记录耗时与父子关系，上报到 SkyWalking/Zipkin/Jaeger，据此还原调用链与定位慢节点。

=== 分布式 ID 生成方案有哪些？

- UUID（无序，索引差）、数据库号段（批量分配）、Redis 自增（依赖 Redis）、雪花算法（趋势递增，需处理时钟回拨）。
- 雪花：时间戳 + 机器 ID + 序列号。

=== 你的项目如何做技术选型与权衡？

- 答题框架：需求（QPS/数据量/一致性）→ 候选方案对比（性能/成本/维护/团队熟悉度）→ 选择与理由 → 权衡与取舍（强一致 vs 最终一致、同步 vs 异步）。
- 结合自己项目：如选 MySQL 而非 TiDB 因团队熟悉与成本；选 Kafka 而非 RocketMQ 因大数据场景等。

=== 什么是 SDD？用 AI 工具做规格驱动开发要注意什么？

- 定义：Spec-Driven Development，先产出结构化、可验收的规格文档，再由 AI 依据规格生成计划、任务与代码，规格是全过程唯一事实源；相对 "vibe coding" 更工程化、可控。
- 流程：Specify（规格）→ Plan（计划）→ Tasks（任务）→ Implement（实现）→ Verify（验证），每阶段人工确认后再进入下一阶段。
- 原则：规格先行、单一事实源、可验收、分层拆解、小步可验证、人掌舵 AI 执行、约束上下文、可追溯。
- 注意坑：规格模糊或过大、代码与规格不同步、跳过 Plan 直接改代码、直接信任生成结果、上下文污染、规则文件膨胀、未声明禁区、敏感信息入上下文。
- 工具：Cursor 用 `.cursorrules`/`.cursor/rules/*.mdc` + Plan 模式 + `@file` 精确上下文；CodeBuddy 用 `CODEBUDDY.md`/`.codebuddy/rules/` + Ask→Plan→Craft 模式 + 检查点回滚。

=== 字段级权限怎么设计？如何让销售看不到进货价？

- *定位*：功能权限（能不能调接口）→ 行级权限（能不能看这行）→ 字段级权限（这行里哪些列能看/能改），三层叠加。
- *配置*：登记敏感字段元数据（默认拒绝），规则按「主体（角色/用户/部门/岗位/租户）× 资源（接口/报表）× 字段 × ABAC 条件 × 效果（ALLOW/DENY/MASK/READONLY）」建模，放配置中心 + 本地缓存；多角色按 *DENY 优先*。
- *实现*：前端隐藏不安全；推荐 *SQL 层列裁剪*（MyBatis 动态 `<if>` 或按角色视图，禁止 `SELECT *`）+ *序列化出口统一脱敏*（`ResponseBodyAdvice` / `@JsonView`）双保险。
- *一致性*：详情、列表、导出、报表、日志、消息、搜索索引、开放 API 走同一套可见字段集合；写操作按可写字段白名单拷贝，别把请求体直接透传。
- *加分点*：防越权推断——字段不返回但允许按它排序/过滤/聚合，仍可反推出值；还要考虑缓存、动态 SQL 执行计划、配置变更实时生效、审计与自动化回归。详见「字段级权限设计（列级数据权限）」。
